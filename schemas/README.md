Every document carries its contract and version in a `schema` field (`"assay.run/1"`). Unknown fields are rejected (`additionalProperties: false`) with two deliberate exceptions, both maps whose keys the spec leaves open:

- the keys of `artifact_names` in `assay.run/1` (one per-job nonce name per job; each value must still be a non-empty string);
- `data` in `assay.event/1` for the kinds whose fields 03 §6 does not list (`RunRequested`, `PlanComputed`, `CoordinatorFinished`, `FindingRaised`, `DecisionMade`, `CheckPublished`, `RunSuperseded`, `BudgetDeferred`, `SlotBusy`, `LedgerWritten`, `SlotReleased`); it must still be an object. The `assay-domain` types are stricter and refuse any field there, so a field added to one of these kinds needs every reader upgraded first (#147).

Text caps (`maxLength`, counted in characters) reject over-length input rather than truncating it.

`assay-app` embeds these files and validates every document on read (`ContractValidator::read`), refusing outright a document over 8 MiB (`MAX_DOCUMENT_BYTES`) or one in which an object repeats a key; a rejection is disposition `schema`, and its error never quotes the document (keys the schema does not name are reported as `*`). A version is never edited once released: a new version is a new file plus an upcast, and is a human decision (H-16).

`fixtures/<contract>/valid/` and `fixtures/<contract>/invalid/` are the golden documents. `crates/assay-app/tests/it/contract.rs` accepts every valid one, and rejects each invalid one at the JSON Pointer and keyword it lists; an invalid fixture without an entry there fails the test. `fixtures/event/domain-invalid/` holds the reverse: documents the schema accepts and the `assay-domain` types refuse (`run-requested-with-data.json`, data on a kind whose fields 03 §6 does not list, #147). `contract.rs` accepts each, and `crates/assay-domain/tests/it/round_trip.rs` refuses each with the message it lists, as it does every invalid event and decision fixture. `assay.run-inputs/1` is not a `Contract`: `assay-app` writes it and reads it back (replay, `assay status`, and the next run's carry set, #224) through its own strict serde DTO, since a bundle may pass the 8 MiB contract-read cap; `crates/assay-app/tests/it/publish_persist.rs` checks its fixtures the same way and validates every bundle `publish` writes against it. The four ledger record contracts (#70) are not `Contract`s either: `assay-app`'s ledger operations write them and read them back through strict serde DTOs (one per JSONL line, or the state document); `crates/assay-app/tests/it/ledger_schema.rs` checks that schema and reader accept every valid golden under `fixtures/ledger-*/valid/` and refuse every invalid one, each at the pointer and keyword it lists, and that every record the writer produces passes its schema. The ledger goldens are each one line in the exact bytes assay writes, and the reader is given those bytes unchanged, since it refuses any other form of a record (`NotCanonical`). Uniqueness rules (one record per key, `seq` in sequence, a cost record's `at` in its file's month) span lines and are enforced by the reader alone. The three lease contracts (#71) are the commit messages of the ledger's lease refs: `assay.ledger-lease/1` on `refs/heads/slot-N`, `assay.ledger-lock/1` on the publish lock `refs/heads/lock-<repo_id>-<head_sha>`, and `assay.ledger-grant/1` on a one-shot retry-grant ref. Their goldens follow the same rules (one canonical line, checked by the same test); the reader also accepts the one trailing newline a git host may add to a commit message, and refuses a document that names another ref than the one it was read from. `assay.context-pack/1` (#72) is not a `Contract` either: `admit` writes it and nothing in assay reads it back yet; `crates/assay-app/tests/it/admit_pack.rs` checks that every valid golden under `fixtures/context-pack/valid/` passes the schema and every invalid one fails it, and that a pack `admit` builds, with suppress text and prior findings, passes it.

`assay.run-decision/1` (#61 DO-6, D5) is a `Contract` like the first five: decide-only's decision bundle is at most 8 MiB (`MAX_DECISION_BUNDLE_BYTES`), so `ContractValidator::read(Contract::RunDecision, ..)` reads it, and `crates/assay-app/tests/it/contract.rs` checks its goldens with the others. `assay-app` also reads it through a strict serde DTO (`read_decision_bundle`), which accepts exactly what `prepare_decision` writes; `crates/assay-app/tests/it/redecide_bundle_read.rs` checks that it accepts every valid golden under `fixtures/run-decision/valid/`, refuses each one-rule edit of a valid golden that the schema refuses, and refuses edits the schema allows but the writer never makes (events out of order, of another run or time, a command event of another comment, voids, waivers or an override the bundle does not record), and `redecide_bundle.rs` that every bundle `prepare_decision` writes passes the schema. The valid goldens are `prepare_decision`'s own output, pretty-printed; each invalid one is a minimal document (empty `inputs` and `decision`, few and short texts, so `redaction.rs` can check that no rejection quotes it) that breaks one rule. Its `github` lists are narrowed by the base tip, so `maintainers` and `agents` may hold 128 identities (`owners` and `approvers` 64).

The `assay.status/1` goldens in `fixtures/status/valid/` (success, failure with blockers, in progress, pending budget-deferred, refused (#218), no check, forged check ignored) are the exact documents `crates/assay-app/tests/it/status.rs` expects `assay status --json` to produce, and are the fixtures for consumers such as the mod's tests. `local-fresh.json`, `local-stale.json` and `local-missing.json` are the same for `assay status --json --local` (`source: "local"`, #130), which `crates/assay-app/tests/it/status_local.rs` expects. A recorded `assay.event/1` stream of `assay check --local --events`, every line valid and in `(job, idx)` order, is `crates/assay-app/tests/fixtures/events/check-local.jsonl`; `crates/assay-app/tests/it/check_events.rs` produces it byte for byte.
