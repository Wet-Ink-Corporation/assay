# 06 · Operations: auth, quota, cost, failure modes, rollout

Status: **v1.2**. Rollout phases are named **M0–M6** (milestones) so they do not collide with principles P1–P10.

## 1. Auth and quota model

- **Mechanism.** `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token`. Preflight runs inside the `review` job (the only job with the secret): `claude auth status` (JSON by default; no `--json` flag assumed), require `authMethod == "oauth_token"` (and, failing closed on 2.1.296's shape, `loggedIn: true` and `apiProvider: "firstParty"`, with `claude --version` equal to `claude_cli`; #83, `03 §7`); assert `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` and provider variables are unset (an API key outranks the OAuth token and silently bills the API); verify the `system/init` message of the first call is clean: no MCP server, tools exactly `Glob`, `Grep`, `Read`, and only built-in plugins, skills and agents on the allowlist pinned next to `claude_cli` (built-ins are allowlisted, not absent: they cannot be switched off headlessly), and pass the hook, mod and AGENTS.md canaries (`03 §8`; `init` has no hooks field) (`init-unclean` otherwise). The built-in `cc-plugin-telemetry` mod sends Anthropic-bound analytics from Z3; it reaches only Anthropic hosts, inside the egress allowlist (`05` T2), and carries what the CLI reports about the session, not the token.
- **What "cost" means.** The CLI's `total_cost_usd` is a client-side estimate at list prices, not billing. On a subscription nothing is charged; assay treats it as **AEU** (API-equivalent units), a relative measure of consumption. AEU is **not** a quota: the Max limit is a rolling 5-hour window plus a weekly window, shared across all Claude surfaces including the owner's own agent sessions, with model-specific limits.
- **Two series are tracked.** (1) AEU per run/tier/role (relative cost, drives caps). (2) Observed rate-limit state from `rate_limit_event` messages in the `stream-json` output (`RateLimitObserved`), per subscription. The event carries `status: allowed|allowed_warning|rejected` and fires with `allowed` routinely, so assay **pauses the LLM stage** on `rejected` or `allowed_warning` only, classifying the state `QuotaExhausted` and deferring (below). A `setup-token` OAuth token carries only the `user:inference` scope and cannot read plan utilisation, so there is **no utilisation-based pause** (v1's "≥ 70%" rule is removed, `A-13`). Because review and authoring share one window and are correlated (a burst of agent PRs is a burst of reviews), a daily dollar cap alone does not protect the window; the pause-on-signal rule and the semaphore do.
- **Terms (`A-01`).** Max limits assume ordinary individual usage; Anthropic reserves enforcement. This design is for the owner's own private repositories only. Tripwires: terms change; throttling of CI use; the reported announcement that headless/Agent-SDK/GitHub-Actions usage moves to a separate monthly credit (**unverified**: only secondary sources were reachable; check the official support article at M0 sign-off and quarterly). Response: set `runner = "claude-api"`; monthly cost at API prices is bounded by the AEU estimates in `01 §8` (≈ $282–$423 at 10–15 PRs/day, a lower bound).

### Caps

| Cap | Value | Basis / enforcement |
|---|---|---|
| Per role call | `Cap (AEU)` in `04 §3` | `--max-budget-usd = cap` exactly, plus `--max-turns` and a wall-clock timeout. The flag is a client-side estimate that "can pass the cap by up to one response"; `total_cost_usd` is emitted only in the final `result` message, so mid-run killing on assay's own accounting is not possible (SIGTERM yields exit 143 and loses both output and cost). The real cost of every call, including `error_max_budget_usd` / `error_max_turns` results (which carry `total_cost_usd` and `modelUsage` but no structured output), is ledgered |
| Per run | sum of role caps: micro $0.25; lite **$0.74**; full $2.30; full + `meta` $2.60; sharded full ×shards (≤ 3): $6.90 / $7.80 | remaining roles skipped when the run cap is reached |
| Per PR per hour | 3 admissions (`reserved` records), then deferred | T12 |
| Per day, per subscription | **$40 AEU** (`A-13`, provisional) | ≈ 2.1× expected spend at 15 PRs/day ($19.2); leaves room for interactive use. (v1's $30 was only 1.56× the corrected load) |
| Eval ledger | $150 AEU/month, separate | `04 §8`; never draws on the production cap |
| Concurrency | **2 model-running `review` jobs across all repos** (semaphore below); ≤ 4 model processes per run, shards sequential | `A-03`, `ADR-19` |

`A-13` is provisional. Calibration (M2 for lite/micro, **M3 for full**, ≥ 7 days wall clock to see the weekly window) replaces it with measured values: AEU per tier, window consumption, and behaviour at limits. Measurement is done by observing production-shaped load off-hours at ≤ 50% of the guardrail; deliberately driving the account to throttle is avoided because it consumes the owner's interactive quota.

### Deferral and requeue

Two different conditions, two different handlings (rubric rule 8):

- **Deferral** (quota or infra: `budget-deferred`, `infra-llm-unavailable`; or `slot-busy`, a busy semaphore): records `BudgetDeferred` (or `SlotBusy`), writes a **deferral record** `{repo, pr, head, count, resets_at, flag}` to the ledger, shows the reason in the check summary and projects it as label `assay:llm-pending`. Trust-path/exec-surface PRs stay `in_progress` (never `neutral`, which counts as passing for required checks), requeued at most 3 times, after which they fail with `infra-llm-unavailable` so a stuck PR is visible. `slot-busy` on an agent-authored PR does the same, so an agent cannot manufacture a busy semaphore to merge without LLM review (R3-06). Others get `success` with a visible warning (`llm-degraded`); `slot-busy` frequency is reported (§7). Requeue is **event-driven first** (any later PR event) plus a `schedule` every 2 hours (job `requeue`) that selects PRs **from the ledger deferral records, never from labels** (a writer could add or remove a label on any PR, R3-15) and dispatches the base workflow's `workflow_dispatch` entry (`actions: write` held only by this tiny base-defined job; the only input is the PR number, which the workflow re-resolves to the current head SHA and re-validates as untrusted). A decide-only command or an `assay:requeue` label never dispatches: at most it sets `flag` on the deferral record for the next `requeue` pass. Backoff follows `resetsAt` from a `rejected` rate-limit event when present. The dispatch path reuses the same Z0–Z4 topology, and its evidence bundle is accepted by decide-only (`02 §5`).
- **Role budget exhaustion** (a required role hit its own cap, turns or timeout): waiting cannot heal it, so it is `failure (required-role-degraded)` on trust-path/exec-surface PRs, with `/assay retry <role>` or `/assay override llm` as the remedies; on other PRs it is a `llm-degraded` warning. **Retry mechanism (R3-14):** decide-only cannot run a model or dispatch, so it records a one-shot **grant** as an atomically created ref `refs/heads/retry/<repo_id>/<pr>/<head_sha>/<role>` in the ledger (a second retry on the same head and role fails to create it while the first grant waits) and sets the deferral record's `flag`; the `requeue` job, or a release event, dispatches with the PR number only (never a role, cap or factor input, which any writer could supply); `admit` consumes the grant by compare-and-set and applies ×1.5 to that role's cap only when it holds the grant. Consuming deletes the ref, so after it a new grant for the same head and role could be created: the once-per-head-and-role retry limit is enforced by decide-only from its command records, not by ref creation (as built, #71; that enforcement is #287). The retry run re-runs all required roles on the same evidence key; combining evidence across runs is out of scope.

### Ledger and semaphore (central, ADR-19)

GitHub has no API to list check runs by time or app (they are per commit, so force-pushed or superseded SHAs are undiscoverable) and Actions concurrency groups are repository-scoped, so neither the v1 "sum `assay / cost` check runs" ledger nor a cross-repo "2 at a time" rule was implementable. The ledger is therefore a small private repository, `ledger_repo` in base config (`Wet-Ink-Corporation/assay-ledger`), to which the assay App has `contents: write` through a separate installation token (cross-org repos need their own installation):

- **Cost records.** `ledger/YYYY-MM.jsonl`, append-only, compare-and-set on the file `sha`: `{run_uid, run_key, repo, pr, head_sha, tier, roles[{role, aeu}], aeu, kind: reserved|final, cancelled, at}`. `admit` writes a `reserved` record when it acquires a slot; the `release` job writes the `final` record with the real cost, or the run cap when the review died or was cancelled (SIGTERM loses `total_cost_usd`, `03 §8`); the ledger-side `reconcile` back-fills, charged at the run cap with `cancelled: true`, for runs whose `release` never ran. Records are keyed and deduplicated by `run_uid` (R3-16).
- **Budget read.** `admit` (not `plan`, which has no credentials) sums the last 24 h of records (a `reserved` record counts until its `final` record replaces it) plus the `reserved_aeu` of leases that are live **or expired but not yet reaped**. It is synchronous GitHub state, current to within the runs in flight. The read is check-then-act, so two concurrent `admit`s can overshoot the daily cap by at most two reservations (the two slots); this is accepted (R3-27). The per-PR cooldown counts `reserved` records, i.e. admissions, not completions (R3-06).
- **Semaphore.** Slots are refs `refs/heads/slot-0` and `refs/heads/slot-1` in the ledger repo. `admit` acquires one by creating the ref (creation fails if it exists, which is atomic) pointing at a commit whose message carries the lease `{run_uid, repo, pr, reserved_aeu, expires_at}` (TTL 45 min, recorded as `lease_commit` in `admit`'s outputs). The slot spans **only the review**: a Z4 job `release` (`needs: [admit, review]`, `if: always() && needs.admit.outputs.slot != '' && github.run_attempt == 1`) releases it and writes the cost record; `decide` no longer releases. The review job's `timeout-minutes` is ≤ 40, below the TTL, so a live lease never expires. **Release and reap are compare-and-set only**: `git push --force-with-lease=refs/heads/slot-N:<lease_commit> <ledger> :refs/heads/slot-N`, which receive-pack checks atomically against the old value; REST `DELETE /git/refs` (no precondition) is never used, so a stale holder cannot delete a newer holder's lease (`A-33`, R3-06). `admit` reaps expired leases itself, by the same compare-and-set, before it waits; no slot free ⇒ `admit` waits up to 10 min, then defers with `slot-busy`. The ledger-side `reconcile` is the backstop. As built (#71): the lease commit is parentless with the empty tree and its message is one `assay.ledger-lease/1` line (03 §6c); the lock and grant refs below carry `assay.ledger-lock/1` and `assay.ledger-grant/1` the same way; a lease is live through its `expires_at`; a lease assay cannot read is never reaped and makes the ledger unreadable.
- **Reservations** are made only by `admit` and only for runs that will spend (not trivial, draft or needs-split runs, which v1 wrongly reserved, and not runs that reuse a complete evidence record, `02 §5`), and are settled by `release`. A superseded or cancelled run still releases and ledgers: "writes nothing" covers only the check and comments (`03 §5`).
- **Per-PR state records (ADR-23).** Besides cost, the ledger holds the authoritative per-PR state that the check run only projects (`02 §5`): push records `pushes/<repo_id>/<pr>.jsonl` (written by `open`), command records `commands/<repo_id>/<pr>.jsonl` (written by decide-only), per-PR state `state/<repo_id>/<pr>.json` (evidence and decision pointers, evidence records, the deferral record and requeue counter, per-actor command counters; compare-and-set on the file `sha`), retry grant refs `refs/heads/retry/…`, and the per-head publish lock `refs/heads/lock-<repo_id>-<head_sha>` (2-minute TTL; acquired by creation, released and reaped by compare-and-set like the slots).
- **Record shapes and the adapter (#70).** The four file contracts are `03 §6c`. `assay-app` owns the `Ledger` port (read a file whole, write it only if it is still at the version read) and every rule over the records: strict reading, deduplication, the budget read, and the bounded compare-and-set retry (5 attempts, then a typed `Contended` error). `assay-forge`'s `LedgerRepo` implements it over the contents API: `GET contents/<path>` (past 1 MB, the blob by its `sha`), `PUT contents/<path>` with the `sha` read, where GitHub's 409, or its 422 on a create over an existing file, is the conflict. A 404 for a file counts as absent only once `GET repos/<ledger_repo>` shows the token sees the repository, so a token without access is an error, never an empty ledger. A retryable `PUT` failure is resent only after a read shows it did not land. Doctor's access assertion (below) is #75's.
- **One reconciler for shared state.** Exactly one designated `reconcile` job, running in the ledger repo itself, reaps leases and locks and back-fills cost records; each consumer repo's `reconcile` touches only its own checks, so repos do not race to back-fill the same expired lease (R3-16).
- **Access.** Only the `assay-ledger-writer` App writes the ledger (ADR-26): its collaborators are the owner and that App, a ruleset restricts `refs/heads/**` and file updates to it, and agent ids have no access (doctor, `05 §7`, T23).
- The ledger is not telemetry: if it cannot be read, `admit` fails and the LLM-unavailable policy applies; if it cannot be written, `release` and `decide` warn (`LedgerWritten` absent) and `reconcile` back-fills from bundles. Push and command records are the exception: if `open` cannot append a push record the run aborts visibly (S0), and if decide-only cannot append a command record the command has no effect and the reply says so.

## 2. Cost model (per run, AEU)

| Tier | Roles | Expected | Cap |
|---|---|---|---|
| trivial | none | $0 | $0 |
| micro | `combined-micro` | $0.15 | $0.25 |
| lite | `combined` + ≤ 3 verifier calls (3 × $0.08) | $0.50 | **$0.74** |
| full | `bugs`, `security`, `design`, coordinator, ≤ 5 verifier calls | $1.50 | $2.30 |
| full + trust path | + `meta` | **$1.70** | $2.60 |
| full, sharded (≤ 3) | the above per shard, shards sequential | ≤ 3× | $6.90 ($7.80 with `meta`) |

Expected values are assertions until M2/M3 measure them (`A-21`); the caps are provisional for the same reason. One check on plausibility from the reviewers: a full-size 120 KB context pack (~30k tokens) plus ~25k tokens of system prompt/tools, grown over 25 turns, reads on the order of 1.9M cache-read tokens, which at list prices is $0.56–$0.94 before cache writes. A `bugs` cap of $0.60 may therefore be too small for large packs; large packs shard, and the cap is set from the measured p90.

Per PR (all runs): 1 first run at the tier cost plus 1.5 further runs, **each at 100%** because specialists review the full cumulative diff (`04 §7`) ⇒ factor 2.5 (v1 assumed 50% for incremental runs, which nothing in the design supported). Mix 20/25/35/20 (`A-02`): $0.5125 × 2.5 = **$1.28/PR** ⇒ $12.8/day at 10 PRs, $19.2 at 15, **$282–$423/month AEU**. This is a lower bound: the mix prices every `full` PR without `meta` (trust-path PRs are always `full`+`meta`, expected $1.70, so up to ≈ $0.10/PR averaged is missing if trust-path PRs are the whole 20%), and sharded runs are ignored. If trust-path PRs are more than the 20% assumed, the mix is revised from M1 history.

Levers if over budget, in order: (1) raise the `micro` floor; (2) merge `design` into `bugs`; (3) skip the verifier for `lite` majors; (4) **incremental specialists**: review only changed hunks since the last completed run plus a full-diff verifier pass (brings the factor toward 1.5–1.75 at some recall risk, to be measured); (5) cheaper tier for specialists, stronger tier for coordinator/verifier; (6) `security` only when a risk glob or exec surface matched.

**Prompt cache (design, `A-15`).** The specialists of a run share the *same* fixed system prompt, the *same* cwd (an empty directory; the PR tree is `--add-dir`), the *same* tool block and the *same* findings schema, with `--exclude-dynamic-system-prompt-sections`, so their prefix is byte-identical. The context pack comes first in the user message; the role instruction follows it. The first call goes alone for ~20 s so the others hit its cache entry. The coordinator and verifier use different schemas (and possibly a different model tier, which has its own cache namespace), so they **do not** share it; only same-model, same-schema roles do. Reviewers reported that a per-role cwd plus the default system prompt (which embeds a cwd-derived memory path) would have defeated sharing. Target ≥ 30% input saving on the specialist calls; measured via `cache_read_tokens` at M2.

## 3. CI cost and performance

- **Z2b warm build.** No `actions/cache` for any decision-bearing build (the Actions cache can be pre-seeded under the base scope with the run-scoped runtime token, keys are immutable once created, and `restore-keys` returns the newest match, so a poisoned entry would persist after merge and be restored by every later job, `T6`). Instead, a trusted job on pushes to the default branch builds the workspace's dependency `target/` and registry cache and publishes it as a **digest-pinned OCI artifact** to GHCR (the same mechanism as the assay binary, `A-20`); base `.assay/plugins.toml` names it by digest (`warm_target`); Z2b jobs pull it by digest and run `cargo clean -p <workspace crates>` before building, treating it as untrusted input. A stale digest only costs time (a cold build). If the Actions cache is kept anywhere, only for non-decision steps and only with exact keys that contain a main commit SHA, never `restore-keys`.
- **gates duplicate the repo's own `rust.yml`.** Deliberate (a PR can edit `rust.yml`, so its result is untrusted): assay's Z2b runs base-defined fmt, `baseline --check`, `nextest --no-tests=fail`, doctests and `cargo deny`, split across `gates-lint` and `gates-test`. The repo's own workflow remains as developer feedback.
- **Actions minutes (the only cash cost).** Billed per job rounded up to whole minutes (Linux 2-core $0.006/min; 3,000 included minutes on Team; rates from the reviewers' cited GitHub docs). Estimated billed minutes per run: trivial **4** (open, plan, gates-static, decide, each rounded up), micro 12, lite 21, full 34 (the `admit` job and the `gates-test` split add ≈ 1–3 minutes over v1, and the v1.2 `release` job 1 minute on every spending run) ⇒ weighted 0.2×4 + 0.25×12 + 0.35×21 + 0.2×34 = **17.95 min/run**. Scheduled polling per consumer repo per month: requeue every 2 h (360) + reconcile every 6 h (120) + the hourly approval poll (720, `04 §6`; v1.1's uncounted 20-minute poll would have been 2,160) = 1,200 min, × 3 repos (`H-03`) = 3,600, plus 120 for the ledger-side reconcile ⇒ 3,720. At 25 runs/day × 22 days = 550 runs ⇒ 9,873 min + 3,720 (polling) + 1,100 (decide-only, ≈ 2 job-minutes per run) = 14,693 min ⇒ overage (14,693 − 3,000) × $0.006 = **$70/month**; at 15 PRs/day ≈ 825 runs ⇒ 14,809 + 3,720 + 1,650 = 20,179 min ⇒ **$103/month**. (v1's $33–$58 excluded polling, decide-only runs, the trivial 4-job minimum and the new jobs; v1.1's $48–$80 counted polling for one repo and omitted the approval poll, R3-18.) Polling schedules are kept to a 2-hour requeue, a 6-hour reconcile and an hourly approval poll at an off-peak minute instead of 30- or 20-minute crons.
- **Critical-path latency, `full`** (lower-bound sums, optimistic): open 0.5 + plan 1.0 + admit 0.5 + review start 1.3 + first-call stagger 0.3 + slowest specialist (25 turns × ~10 s) ≈ 4.2 + coordinator 1.5 + verifier 2.0 + release 0.5 + decide 1.0 ≈ **12.8 min**; with ordinary variance p50 ≈ 15, p95 ≈ 25 (QA-04). `.rs` PRs wait on Z2b in parallel; with the warm `target/` a lint+test run is 5–10 min. **`trivial`**: runner start 1.3 + open 0.5 + plan 1.0 + decide 1.0 = **3.8 min** before any gate work, hence QA-01's p50 ≤ 5 / p95 ≤ 8.
- **Gate timeouts.** The temper adapter's `timeout_s` (1,200) covers only its own steps (scan in `gates-static`, `baseline --check` in `gates-lint`); the declared steps (`fmt`, `deny`, `tests`, `doctests`) carry their own `timeout_s` (`03 §1`). A timeout is `gate-error`; the Z2b jobs retry once on infra-class errors only.
- **Optional hardening (M2 stretch, not a v1 claim).** Run the Z2b job under a separate low-privilege uid or container with no access to the runner's file-command directories or the Actions runtime token; this would narrow what a hostile `build.rs` can reach. Until built, `T6` states the residual without it.

## 4. Check lifecycle (fixes "stuck pending")

1. `open` (Z0) finds or creates the **single** App check run for (head SHA, check name) and, under the per-head publish lock, sets it `in_progress` with `external_id = pending:<run_id>:<seq>`, so a check always exists once the workflow starts and two same-named check runs never exist on one SHA. It never rewrites `started_at` (the push clock is the ledger push record's `at`, `04 §5`). Reopening a `completed` run is unverified (`A-30`, M1 canary); if GitHub rejects it or keeps the old conclusion, `open` instead publishes a completed `failure (re-deciding)` before the run starts, which is fail-safe.
2. `decide` runs `if: always()` and treats `cancelled`, `skipped` and `failure` of its needs as explicit states, so a failed or timed-out upstream job still ends in a conclusion, **except** that an upstream `cancelled` caused by a newer run for the same head writes nothing and leaves the check `in_progress` for that run (`02 §5`).
3. `decide` (and decide-only) re-fetches the PR head and base ref and writes nothing if either changed; it then takes the per-head publish lock in the ledger, re-reads the stamp, publishes only if the stamp is still the one it read, and releases the lock by compare-and-set (`02 §5`; the check API itself has no compare-and-set, R3-09). The new run's `open` re-stamps the check for the new run.
4. A **reconcile** workflow every 6 hours (default-branch file, App token) in each consumer repo: lists `in_progress` verdict checks older than 2 × the tier p95 with no live workflow run and marks them `failure publish-error`; closes the checks of superseded head SHAs as `cancelled`. It touches only its own repo's checks. The single **ledger-side reconcile** (in `assay-ledger`, every 6 hours) reaps expired semaphore leases and publish locks by compare-and-set and back-fills missing ledger records, deduplicated by `run_uid` (R3-16). Checks labelled `assay:llm-pending` with a requeue still scheduled are excluded; checks in `trust-path-unapproved` are `failure`, not `in_progress`, and are untouched.
5. If the workflow never starts at all (Actions outage), GitHub shows "Expected, waiting for status"; the break-glass is the ruleset bypass by the break-glass account (the only bypass actor, `05 §7`), recorded outside assay and documented in `docs/operations/break-glass.md` (M1 deliverable).

## 5. Failure modes and effects

| ID | Failure | Detection | Effect | Handling |
|---|---|---|---|---|
| F1 | `claude` exits non-zero / malformed output | exit code, schema | Role missing | `Malformed` ⇒ retry once; otherwise degraded role (`required-role-degraded` on trust-path/exec-surface PRs, else `llm-degraded`) |
| F2 | `error_max_budget_usd` / `error_max_turns` (no structured output) | result subtype | Role produced nothing | `SpecialistBudgetExhausted`, **no retry**; the real `total_cost_usd` from the result is ledgered; degraded role visible in the check summary; caps re-sized from p90 (M2). On trust-path/exec-surface PRs: `failure (required-role-degraded)`, remedy `/assay retry` (cap ×1.5) |
| F3 | Quota exhausted / `rejected` rate-limit event | CLI error class, event status | LLM unavailable | Deferral and requeue (§1) |
| F4 | OAuth token expired/revoked | preflight; doctor (recorded expiry) | LLM unavailable | Loud failure + link to `docs/operations/token-rotation.md` (`assay_app::TOKEN_ROTATION_RUNBOOK`, #93); doctor warns from T−30 days (`05 §5`); monthly canary catches early |
| F5 | CLI flag removed/renamed, or flag accepted but ineffective | `assay doctor` on the pinned CLI, `system/init` assertion, hook and fence canaries | Preflight fails | Pin in base config; upgrades are PRs that run the corpus |
| F6 | Model non-determinism flips a verdict | decision replay shows identical decision from stored inputs; fingerprint flip rate across re-runs in `assay report` | Flaky advisory blocker | LLM blockers advisory; promotion requires measured precision |
| F7 | Runner timeout / cancelled by newer push | job status | Half run | `decide always()` + supersede rule + cancelled-by-newer-run rule (§4) |
| F8 | GitHub API 5xx / secondary limit | HTTP | Publish fails | Backoff ×3, then `failure` `publish-error`; reconcile fixes stragglers |
| F9 | Gate flake (registry) | exit class | False failure | Z2b retries once on infra-class errors only; temper findings are never retried. As built (#67, #229): in `gates-test` and `gates-lint` a declared step a signal ended is the only infra-class outcome and is run once more (`baseline --check` is not retried); exit codes are never retried, since cargo's 101 does not tell a registry failure from a compile error, so registry flakes are prevented by the warm `target/`'s registry cache rather than retried (03 §2.1 step 7) |
| F10 | Verifier rejects all / none | live reject rate (`FindingVerified`) outside 10–60% over ≥ 20 runs | Silent quality loss | Alert; confusion matrix on corpus; refuted ⇒ downgrade, not drop |
| F11 | Prompt bundle regression | corpus method (`04 §8`) | Noise/misses | Replay gate on prompt/rubric PRs |
| F12 | Persist (bundle upload) fails | step error | Replay and decide-only impossible for that run | **Trust-path and exec-surface PRs: fail closed** (`failure persist-error`); other PRs: warning, decision still published, and a later decide-only command reports `bundle-expired` and requires a re-run. A bundle older than 90 days, or one deleted by a writer, behaves the same (F20) |
| F13 | Weigh-In journal missing | CP2 evidence rule | Hidden open items | Identity-based evidence rule (≥ 1 journal for agent code PRs); staged rollout (`04 §9`) |
| F14 | Cost spike (retry storm) | per-call cap, per-run cap, hourly cap, ledger | Quota burn | `--max-budget-usd = cap`, `--max-turns`, timeouts, ledgered real costs |
| F15 | Required plan stage disagrees with Z4 recomputation | `plan-mismatch` | Tampered/buggy plan | `failure` (loud) |
| F16 | Ledger repo unreadable or unwritable | API error | Budget unknown / record missing | Read: `admit` fails ⇒ LLM-unavailable policy. Write: warning; `reconcile` back-fills |
| F17 | Semaphore lease leaked (crashed or cancelled `release`, runner loss) | `admit` or the ledger-side `reconcile` sees an expired lease | Capacity reduced | Reaped by compare-and-set by the next `admit` after the 45-minute TTL expires; otherwise by the ledger-side `reconcile` within 6 h. A superseded run's slot is released by `release`, not leaked (R3-06) |
| F18 | Artifact digest does not match the producing job's `outputs` | Z4 check | Possible tampering (or upload race) | `gate-error:artifact-digest` ⇒ `failure`; that artifact is never used |
| F19 | Bundle pointer or provenance check fails in decide-only (wrong workflow file, event, attempt, `head_repository`, a `workflow_dispatch` run not on the default branch, or a digest mismatch) | Z4 check | Possible forgery | Refuse; `failure gate-error:bundle-digest`; no re-decision from that bundle |
| F20 | Bundle artifact missing (expired, or deleted by a writer holding `actions: write`) | artifact lookup by the ledger pointer returns nothing | decide-only cannot re-decide that run | `bundle-expired` (not `bundle-digest`: absence is not forgery); a re-run is required; deletions are reported. Mirroring the decision-critical part into the ledger is an open question (`07 §5`, R3-28) |
| F21 | Per-head publish lock held by a crashed writer | lock creation fails; the lock's TTL has passed | Publication delayed | Reaped by compare-and-set after the 2-minute TTL by the next writer or the ledger-side `reconcile`; a writer that cannot take the lock within its retry budget ends in `publish-error` (S8) |
| F22 | Host lacks a runtime prerequisite of process-group supervision (the git layer, and since #150 the `exec` gates and `claude -p`, through the same `assay-forge` supervisor): a Linux `/proc` describing this process, or a procps/util-linux `kill` in `/usr/bin` or `/bin` (used to kill a timed-out git process group, `03 §9`) | `GitEnvironment::from_process_env` before any git runs (`/proc/self/stat` must name this process's pid, else `KillerError::ProcUnavailable`; no `kill`, `KillerError::NotFound`); `/proc` read errors while supervising | No git operation can be bounded | Fail closed: the job errors before fetching anything (`gate-error`), never runs git unbounded. A `/proc` read error while supervising is `ProcessError::Kill`; a group whose leader is already reaped is then never signalled (its id may be reused), and the job aborts. GitHub-hosted Ubuntu images carry procps; self-hosted runners must too |

## 6. Fail-open vs fail-closed (P6)

| Component | Policy | Rationale |
|---|---|---|
| Required gate (temper; weigh-in once required) | **closed** (including skipped/timeout/invalid) | Compliance; error ≠ pass |
| Rubric/schema validation, `plan-mismatch`, artifact and bundle digests | **closed** | Garbage in cannot yield success |
| `base-not-protected` | **`failure`** (the check is not required there, so nothing is blocked) | A stale result is fail-safe if the head is later retargeted to a protected base; `neutral` counted as passing and opened a retarget-and-merge window (R3-03) |
| Publish | **closed** after retries | A stuck pending check is worse |
| LLM stage unavailable/degraded | **by class**: trust-path and exec-surface PRs (the `block_on_infra_for` classes) ⇒ deferral (`in_progress`, ≤ 3 requeues) or `required-role-degraded` failure; otherwise `success` with a prominent, event-recorded `llm-degraded` warning | The LLM stage is advisory until promoted (QA-05); gates still enforce; quota outages must not freeze the founder for hours |
| Verifier unavailable, coordinator failed | Treated as a degraded stage (above), never a deferral, since waiting cannot heal a cap: the `verifier` or `coordinator` is listed in `degraded` and the PR gets `required-role-degraded` (blocking classes or policy) or `llm-degraded` (`04 §5` rule 8); candidate blockers are shown as *unverified majors*. Weigh-In default wi-9fd143, taken AFK; the owner can reopen it | No silent downgrade |
| Persist (bundle) | **closed** for trust-path/exec-surface PRs; **open** (warning) for others | Approval and replay depend on it |
| Telemetry, ledger write | **open** | Observability must not block merges |

**Path B (smallest thing, 2–4 days).** A base-defined `pull_request_target` workflow running the pinned temper `baseline --check --locked --base <base_sha>` (failing on `ratchet.raised`), plus `claude-code-action@v1` with the OAuth token, a base-sourced REVIEW.md-style prompt and `--json-schema`/`--max-turns`/`--max-budget-usd`, advisory only. It delivers an early version of G1 and G3 with none of the topology above. Reviewers estimate it captures most of the value at a fraction of the effort; the case for the full design is the combination of the hardened gate, the Weigh-In stage, and replay/eval, not LLM review quality (`07 §4`).

**Kill / pivot criteria (decided now).**
- *Effort:* if M1+M2 actual exceed 1.5× their lower bound (> 22.5 days), switch to Path B for the LLM stage and keep the M1 deterministic stack.
- *Quota:* if an average `full` run consumes > 10% of one 5-hour window, or Anthropic terms exclude CI use of the subscription, fall back to the `ClaudeApi` runner and re-baseline cost.
- *Quality:* if after M5 recall is clearly worse than the pinned baseline (QA-07, once the test split can support a statement), adopt claude-code-action + REVIEW.md for LLM review and keep the deterministic stack. Failing QA-05 does not kill the project; it keeps LLM blockers advisory.
- *Reliability:* QA-08 > 3% of PRs held by infrastructure over 4 weeks ⇒ fix or pivot.
