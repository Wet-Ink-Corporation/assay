# 05 · Security and threat model

Status: **v1.1**.

Scope: private-org GitHub repositories; assay on GitHub-hosted runners (default) with a Max OAuth token as the only model secret and a dedicated GitHub App for publishing. Out of scope: GitHub or Anthropic compromise.

## 1. Assets

| Asset | Why it matters |
|---|---|
| `CLAUDE_CODE_OAUTH_TOKEN` (~1 year) | The owner's subscription; exfiltration burns quota and may breach terms |
| `assay-verdict` App private key | Can forge the required check |
| Base branch integrity | What merges |
| The gate itself (workflow, assay digest, tool pins, config, rubric, prompts, owners/agents lists) | If a PR can edit it, the gate is advisory |
| Persisted bundles / events / ledger | Audit trail and budget state; must not be forgeable by a PR or a workflow it adds |

## 2. Adversaries

- **A1** Hostile, steered or careless agent author (including the owner's own cloud sessions steered by injected content). Pushes under an agent identity (`H-08`).
- **A2** Prompt-injection carrier: PR body, comments, commit messages, filenames, code comments, dependency READMEs, fixtures, `.claude/` content in the head tree.
- **A3** Dependency/supply-chain: a new crate whose build script runs in Z2b.
- **A5** A collaborator (or a workflow they add on a branch) who can run workflows, upload artifacts under any name, post comments, edit PR metadata and trigger decide-only runs; and a hostile process in Z2b holding the run-scoped Actions runtime token.
- **A4** Insider mistake: owner merges on a stale or overridden check.

## 3. Threats and mitigations

| ID | Threat | Mitigation | Residual |
|---|---|---|---|
| T1 | **Prompt injection steers a reviewer** (says "no issues", suppresses a finding, writes malicious comment content) | Untrusted envelope; reviewers read-only, cannot approve (P1); schema + evidence + trigger validation; blind verifier; injection screen (secondary); **LLM output can never lower a gate finding**; LLM blockers advisory until promoted | An injection can still *suppress LLM findings* (a false negative). Accepted: gates are the compliance backstop. `corpus/inject/` measures it on every evaluation |
| T2 | **Token exfiltration from Z3** | No Bash/WebFetch tools (`--tools Read,Grep,Glob` plus `--restricted`), because allowlists do not remove the built-in read-only Bash set and `Bash(rg:*)`/`git --output` permit execution/writes (reproduced); cwd is an empty directory, PR tree via `--add-dir`; `--safe-mode` + `disableAllHooks` + clean-init assertion from `system/init` (MCP servers, plugins, skills, agents) and the **hook canary** (hooks are not visible in `init`; project hooks, skills, MCP and `allowed-tools` otherwise run in `-p` even in untrusted folders); `permissions.deny` for `/proc`, `/sys`, `~`, `/etc` and `permissions.blockReadsOutsideWorkingDirectories`; the **fence canary** (`Read //proc/self/environ` must appear in `permission_denials`); `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` (moot with no spawning tool); **mandatory egress allowlist** (`api.anthropic.com`, `github.com`) in block mode; **output-channel scan** (T8): a steered model needs no network, it can write the token into `title`/`body`/`fix`/`trigger` for Z4 to post where a collaborator reads it, so the assay process scans every free-text field in Z3 and again in Z4 for the token and its encodings and for unexplained long alphanumeric runs (`03 §3`), fails the job and flags rotation on any hit | The token sits in the claude process's initial environment, and the in-process `Read` tool is not covered by subprocess scrubbing. If a deny rule is bypassed the token is readable; the output scan catches the plain and common-encoded forms, not an adversarial cipher over a long horizon. Defence in depth, not proof. If `A-12` (egress block mode) fails verification, Z3 moves to a container/self-hosted runner with a network policy before launch |
| T3 | **PR edits the workflow / assay digest / pins to skip the gate** | `pull_request_target`: workflow, digest, pins, rubric, prompts, owners, agents all from base SHA. Edits to them are trust-path changes (R-07): `full`, `meta`, owner approval. Branch protection restricts workflow-file edits to the owner (`§7`) | A PR that changes them is reviewed *as a change* and takes effect only after merge |
| T4 | **Vendored temper (`.claude/temper/`) changes what the gate reports** | assay runs temper from a pinned commit/digest; the PR's copy is ignored; its drift versus the pin is a `major` finding; changes to it are trust-path | None additional |
| T5 | **Temper config/baseline weakened** (raise baseline, relax `gate`/`scanner` keys, `gate.steps`, `#[expect]`, test deletion/ignore, manifest test switches, lints table or lint inheritance, clippy.toml, `.gitattributes` blinding or LFS filters) | In **Z2s** (not forgeable by `build.rs`): `raised` from a totals diff of the baseline file, `exception` from the pinned `temper scan`, gate-config key drift, test inventory, manifest switches, lints-table diff and lint inheritance; `git check-attr` forbids `diff`/`text`/`filter` attributes on changed Rust and manifest files; in Z2b only clippy/rustdoc counts, with `ratchet.mode == diff+totals` asserted and the ratchet base recomputed independently. clippy/rustfmt/rust-toolchain/`.gitattributes` are trust paths (`04 §2.2`; the temper-specific list is `03 §2.1`). Verified: temper's `baseline --check` exits 0 on a raise and ignores `ask` exceptions; `temper gate` has no base; its protections for tests/switches are hook-only; an explicit `--base` overrides `TEMPER_BASE` | If temper itself has a hole the ratchet misses, assay inherits it; the contract requests `D-TEMPER-1` (gate-config diff as a CLI subcommand) and `D-TEMPER-2` (compare blobs rather than hunks) close the file-parsing and hunk-oracle gaps upstream |
| T6 | **Z2b executes hostile PR code** (build.rs, proc-macros, tests, `.cargo/config`) and forges its own gate result, forges another job's artifact, or poisons shared state | Z2b has no secrets and `contents: read`; `persist-credentials: false`; **split into `gates-lint` (clippy/rustdoc/ratchet counts; runs build.rs and proc-macros, which are owner-approved exec surface) and `gates-test` on a different VM** (a hostile test can then lie only about test results); **no `actions/cache` for any decision-bearing build**: the warm `target/` is a digest-pinned OCI artifact produced by a trusted main-branch job (the Actions cache can be pre-seeded under the base scope with the stolen runtime token, keys are immutable once created and `restore-keys` returns the newest match, so a poisoned entry would persist after merge); **every artifact Z4 consumes must match a digest in the producing job's `outputs`** (the runtime token lets a hostile process list, overwrite and delete artifacts of the whole run, so only an output digest authenticates the Z2s→Z4 channel); per-job nonce names; Z4 recomputes everything derivable (trust paths, tier, fingerprints, required plugins) and treats gate `pass` as weaker evidence than gate `fail`; **static checks (scanner, `raised`, manifests, test inventory, lint inheritance) run in Z2s with no PR-controlled execution**; the exec surface is owner-approved territory (R-07) | **A hostile `build.rs`/proc-macro can make `gates-lint` lie, and can differentiate clippy runs from release builds (macro-generated tokens are invisible to the regex scanner).** This is inherent to any CI that compiles PR code. G1's assurance is stated honestly in `01 §1`. Compensating control: owner approval of the exec surface, precisely detected (`04 §2.2`). Running Z2b under a separate low-privilege uid/container with no access to the runner's file-command directories or the artifact token is a hardening option recorded in `06 §3` (M2 stretch), not a v1 claim |
| T7 | **Forged required check from a workflow the PR adds** | All workflows share the "GitHub Actions" app, so an app-id pin does not help. The verdict is published only by the dedicated `assay-verdict` GitHub App; the ruleset requires that `integration_id`; idempotency lookups match `check_run.app.id`; the App key lives in an environment reachable only by `open`/`decide` jobs of base-defined workflows | The owner (App/ruleset admin) can still alter everything; compromise of the App key is a total break (rotated annually; key never in Z1–Z3) |
| T8 | **Comment-based exfiltration/phishing/write-by-proxy** (image beacons, links, mentions, HTML, one-click ` ```suggestion ` blocks) | Z4 sanitiser: HTML/images/mentions stripped, link allowlist, ` ```suggestion ` fences stripped (NG1), length caps, token-shaped strings blocked | None known |
| T9 | **Override/approval/waiver/dismissal abuse; self-approval** | One eligibility rule everywhere (`04 §5`): a numeric user id in `.assay/owners` ∪ `approvers` that is not the PR author, a GitHub-attributed author or committer of the head, or the recorded push sender (P10, `H-08`, `H-13`); approval must be on exactly `head_sha` and later than the push clock recorded in the App-authored check (there is no API listing ordinary pushers); co-author trailers ignored; waivers are scoped to human-decision gate findings, so whole-verdict override stays rare; self-dismissals are logged and ignored; gate/Weigh-In findings can never be dismissed; every override and waiver is in the weekly report; any collaborator may *trigger* a decide-only run (cost only, rate-limited by actor) but privileged outcomes still require an eligible id | If the owner shares credentials with an agent session, or Claude Code cloud sessions push through the owner's GitHub authorisation (`H-08`, unverified), this control is void and P10 is a convention. `assay doctor` checks that the agent identity is not an owner and has no approval right |
| T10 | **Stale or mismatched check** | One App check run per (SHA, name) updated by compare-and-set on check id and `external_id`; `external_id` is `pending:<run_id>` until `decide` sets `decision_key` (which includes `head_sha`); Z4 re-fetches the head and writes nothing if superseded; a `decide` whose upstream was `cancelled` while a newer run exists for the same head writes nothing (otherwise a cancelled run could publish a final `failure` that makes the newer run's identical-key `decide` a no-op); "require branches up to date" enabled; concurrency per `02 §5` | Merge queues are unsupported (NG6). Whether two same-named check runs on one SHA resolve latest-wins is untested, so the design never creates two (canary in M1) |
| T11 | **Artifact/output tampering between jobs; forged bundle** | Per-job nonce artifact names; **sha256 of every consumed artifact equals the producing job's `outputs` digest**; the persisted bundle is trusted by decide-only only through the pointer `{bundle_run_id, bundle_sha256}` in the App-authored check, after verifying that the run is of the assay workflow file, event `pull_request_target`, `head_repository == repo`, and the digest matches (artifact names are a repo-wide namespace that any PR-added workflow can write to; selecting "the latest bundle for the head" would let a branch workflow forge a passing bundle and obtain a genuine App-authored `success`); evidence reuse only via a digest stored in an App-authored record; schema validation; `run.json` not trusted (recomputed); no reliance on `actions/attest` inside jobs that run PR code | A compromised runner (out of scope) |
| T12 | **Quota-exhaustion DoS and self-DoS** | Daily cap, per-PR cooldown (≥ 3 runs/h ⇒ later runs deferred), draft PRs run gates only, a central semaphore of 2 model-running jobs (`ADR-19`), reservations made only by `admit` for runs that will spend and released by `decide`; `edited` triggers only on `changes.base`, and `cancel-in-progress` applies only to `synchronize` (so an agent's repeated `gh pr edit` cannot livelock a long review); decide-only has a non-cancelling group and is idempotent, so GitHub's replacement of a pending job by a newer pending job loses nothing; decide-only commands are rate-limited by actor, require `types: [created]`, a command prefix, `sender.type != 'Bot'`; deferral never *lowers* a verdict: it leaves the check `in_progress` for trust-path PRs (≤ 3 requeues, then `failure`) and shows a visible warning otherwise | Owner-visible, not silent |
| T13 | **Terms/account risk** of subscription CI use | Single-owner private repos (NG3); preflight; `ClaudeApi` adapter; A-01 tripwires including the reported Agent SDK credit change (unverified) | Residual vendor risk, accepted |
| T14 | **Supply chain of assay itself** | `cargo deny`; pinned lockfile; digest-pinned releases; release workflow only from protected tags; sibling tools pinned by **commit SHA/digest** (tags are movable); all actions SHA-pinned in the template | Standard residual |
| T15 | **Base retargeting after the check passes / non-default base** | `edited` with `changes.base` is a trigger; the workflow has **no `branches:` filter** (a filter would make the workflow not run on a retarget to an unprotected base and leave the earlier `success` on the same SHA); `protected_bases` enforced by Z4 (`neutral base-not-protected`, overwriting any earlier conclusion on the single check run); the ruleset applies the required check to the protected branches; `external_id`/`output.text` carry `base_sha`; evidence and decision keys include `base_sha` | A new protected branch needs `.assay` config on it |
| T16 | **Bootstrap: assay gates assay** | For the assay repo, all of `crates/**` (forge, runner and app included), rubric, prompts, schemas, workflows, release workflow, `.assay/**` and `deny.toml` are trust paths; the `assay-self` gate replays `decide` over the golden corpus and fails on any byte change absent an owner-approved snapshot update; release attestation verification (where the plan supports it) names `--signer-workflow` and `--source-ref refs/tags/v*`, tags protected; the genesis commit SHA is recorded in the genesis ADR (`docs/decisions/0001-genesis.md`, M0 deliverable) | The first tree is trusted by construction (owner review) |
| T17 | **Classification gaming** (fake `@generated`, `vendor/`, docs-only claims, lockfile-only, config-as-code, renames out of risk globs, PR splitting, padding, `.gitattributes` binary markers) | Exclusions from base globs only; `.rs`/scripts/manifests never excluded; lockfile dependency changes tier `lite` + `cargo deny`; `trivial` only for the explicit base docs allowlist (no executable agent instructions, no `include_*!` targets); code never `trivial` (`micro` exists); risk and trust globs match both sides of a rename; binary `numstat` (`-`) counts as maximum size; file list from `git diff`, cross-checked with the REST list (3,000-file truncation) | **PR splitting** (30 PRs of ≤ 20 lines) is not aggregated; accepted for v1, recorded in the weekly report as lines/author/day |
| T18 | **Weigh-In evidence is self-attested** | `04 §9`: decisions need one owner ack per PR bound to a digest of the blocking set; blocking set from triaged fields, untriaged items are `pending-triage`; evidence rule keyed to agent identity, not trailers, and requires ≥ 1 journal for agent-authored code PRs; journal append-only check at event level; staged rollout | Until `D-WI` ships, G2 is partly convention (stated) |
| T19 | **Workflow-template hygiene** | `persist-credentials: false` on every checkout; explicit minimal `permissions:` on every job; no `pull-requests: read` for Z3; all third-party actions pinned by full SHA; no cache restore from a scope a PR can write and no cache write in `pull_request_target` jobs; checkout by immutable `head_sha`; **no `${{ github.event.* }}` or `${{ needs.*.outputs.* }}` expression inside any `run:` of a job holding the App key or the model secret: such values are passed through `env:` and read as shell variables** (expression injection); repo setting "Allow GitHub Actions to create and approve pull requests" off | — |
| T20 | **Decide-only is triggered through a PR-controlled workflow file** | `pull_request_review` and `pull_request` `labeled` run the workflow file from the PR merge commit, so a PR that edits `assay-decide.yml` would execute its own version with the App key whenever the owner approves (the approval would silently not update the check, deadlocking exactly the trust-path PRs that need approval). The decide-only workflow is therefore triggered only by events that run the default-branch file: `issue_comment[created]`, `pull_request_target` `labeled`/`unlabeled`, and `schedule`. `assay doctor` fails if any assay workflow in the repo declares a PR-merge-commit trigger. Canary in M1: edit the decide-only workflow in a PR and approve it | None additional |

## 4. Token and permission matrix

Every job also sets `packages: read` where it runs the assay binary (the GHCR digest pull, `A-20`) and `actions: read` where it reads a prior run's artifacts. The App token minted for each job is narrowed per job (`repositories`, `permissions`).

| Job / workflow | `permissions:` / token | Secrets | PR code run | Network |
|---|---|---|---|---|
| open | App token: `checks: write` (consumer repo only); `packages: read` | App key (env-scoped) | no | GitHub API |
| plan | `contents: read`, `pull-requests: read`, `packages: read` | none | no | GitHub API |
| gates-static | `contents: read`, `packages: read`, `actions: read` | none | no (pinned base tools on sanitised copies only) | registries for `cargo fetch --locked` only |
| gates-lint | `contents: read`, `packages: read` (warm `target/`) | none | **yes** (build.rs, proc-macros) | registries (crates.io), GitHub; ideally network-isolated after `cargo fetch` of the locked set |
| gates-test | `contents: read`, `packages: read` | none | **yes** (tests) | as gates-lint; different VM |
| admit | App token: `checks: read`, `pull-requests: read` on the consumer repo; `contents: write` on the ledger repo; `actions: read`; `packages: read` | App key (env-scoped) | no | GitHub API |
| review | `contents: read`, `packages: read`, `actions: read` (the context pack) | `CLAUDE_CODE_OAUTH_TOKEN` (env-scoped) | no | `api.anthropic.com`, `github.com` only (block-mode egress) |
| decide | App token: `checks: write`, `pull-requests: write`, `contents: read` on the consumer repo; `contents: write` on the ledger repo; `actions: read`; `packages: read` | App key (env-scoped) | no (fetches git objects as data, hardened, `03 §9`) | GitHub API |
| decide-only | as decide (default-branch workflow file only) | App key (env-scoped) | no | GitHub API |
| requeue | App token: `actions: write` (dispatch) on the consumer repo; `contents: read` on the ledger repo | App key (env-scoped) | no | GitHub API |
| reconcile (scheduled, default branch) | App token: `checks: write`, `contents: write` on the ledger repo; `actions: read` | App key (env-scoped) | no | GitHub API |
| canary (monthly) / report (weekly) | `contents: read`; canary additionally the model secret; report additionally App `contents: write` on the ledger repo | OAuth token (canary), App key (report) | no | as the relevant job |
| ingest (later, separate workflow) | `contents: write` on the telemetry branch only | — | no | GitHub |
| release: build (assay repo, protected `v*` tag; `docs/operations/release.md`) | `contents: read` | none | no (assay's own tagged commit on `main`) | crates.io, GitHub |

| release: release-notes | `contents: write`; checks out and runs no repository code | none | no | GitHub API |

The default `GITHUB_TOKEN` permission is read-none org-wide; every job sets explicit `permissions:`.

## 5. Secret handling

- OAuth token from `claude setup-token` in an environment (`assay-review`) available only to the `review` job of base-defined workflows (branch policy). App key in `assay-publish`, available only to `open`, `admit`, `decide`, decide-only, `requeue`, `reconcile` and `report` of base-defined workflows (default-branch file, never a PR-merge-commit file).
- Rotation: expiry recorded at creation; `assay doctor` warns at T−30 days; a monthly canary workflow runs the preflight and fails loudly.
- assay never logs the environment; CLI debug output is off; uploaded artifacts are scanned for token-shaped strings (job fails if found).

## 6. Prompt-injection posture (summary)

Defence in depth: *structure* (untrusted envelope, blind roles), *capability* (no Bash, no env, empty cwd, egress block), *validation* (schema, evidence, trigger, screens), *adjudication* (deterministic, models cannot approve), and *asymmetry* (an injection can at worst hide an LLM finding; it cannot forge a gate, a check, or an owner action). LLM review's contribution to the merge decision is advisory until measured (QA-05), so the blast radius of a successful injection is "a missed review", not "a bypassed gate".

## 7. Prerequisites enforced by `assay doctor` (NG2)

Read via the API at preflight and weekly; failures are loud and block LLM review of the repo until fixed:

- Ruleset on the protected branches requires check `assay / verdict` with the `assay-verdict` App `integration_id`; "require branches up to date" on; no bypass actors except the owner. A bare "required review on `.github/workflows`" is **not** sufficient: a feature-branch push can run its own workflow, which is why the check source, the artifact digests and the bundle pointer are all authenticated by the App and by output digests rather than by workflow-file protection.
- No assay workflow in the repository declares a trigger that runs the workflow file from a PR merge commit (`T20`).
- File-path restriction or required review on `.github/workflows/**`, `.assay/**`, `.claude/**`, `CODEOWNERS`, `.gitattributes`.
- Agent identity (`.assay/agents`) is not in `.assay/owners`, has no approval/bypass rights and no `issues: write` rights beyond comments; Actions may not create/approve PRs. An approver account exists (`H-13`) and is not an agent. `H-08` feasibility (agents push under a non-owner identity) is checked behaviourally in M1.
- Environments, egress policy and pinned digests as above; actions in workflows pinned by SHA.
