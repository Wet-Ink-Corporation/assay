# 05 · Security and threat model

Status: **v1.2**.

Scope: private-org GitHub repositories; assay on GitHub-hosted runners (default) with a Max OAuth token as the only model secret and a dedicated GitHub App for publishing. Out of scope: GitHub or Anthropic compromise.

## 1. Assets

| Asset | Why it matters |
|---|---|
| `CLAUDE_CODE_OAUTH_TOKEN` (~1 year) | The owner's subscription; exfiltration burns quota and may breach terms |
| `assay-verdict` App private key | Can forge the required check |
| `assay-ledger-writer` App private key | Can rewrite ledger state: cost and command records, push records, slots and locks (ADR-26) |
| Base branch integrity | What merges |
| The gate itself (workflow, assay digest, tool pins, config, rubric, prompts, owners/agents lists) | If a PR can edit it, the gate is advisory |
| Persisted bundles / events / ledger | Audit trail and budget state; must not be forgeable by a PR or a workflow it adds |

## 2. Adversaries

- **A1** Hostile, steered or careless agent author (including the owner's own cloud sessions steered by injected content). Pushes under an agent identity (`H-08` (a)); a session that also holds the owner's GitHub authorisation can comment, review, label and merge as the owner, which is why privileged identities must never be agent-reachable (`H-08` (b), R3-01).
- **A2** Prompt-injection carrier: PR body, comments, commit messages, filenames, code comments, dependency READMEs, fixtures, `.claude/` content in the head tree.
- **A3** Dependency/supply-chain: a new crate whose build script runs in Z2b.
- **A5** A collaborator (or a workflow they add on a branch) who can run workflows, dispatch `workflow_dispatch` against any branch, re-run any run or job for 30 days, upload and delete artifacts, post comments, **edit or delete other users' comments**, edit PR metadata, add or remove labels and trigger decide-only runs; and a hostile process in Z2b holding the run-scoped Actions runtime token. Agent identities have write access, so they are A5 as well as A1.
- **A4** Insider mistake: owner merges on a stale or overridden check.

**Accepted residuals inside T6's exec surface (#210, owner 2026-11-01).** Each is reachable only by PR code that already runs in Z2b, which is owner-approved territory (R-07), and none can forge another job's result:

- *`exec` program resolution.* A base-declared `exec` gate whose `program` is a relative path with a directory part (`scripts/check`) is resolved against the head checkout (`assay-gates` `exec::resolve`), so the file it runs is PR-controlled; a bare name is looked up on the gate environment's `PATH`. Base declares what runs, the PR decides its bytes; a base that must pin the bytes names an absolute program outside the checkout.
- *Cargo `[alias]`.* A PR's `.cargo/config.toml` can define `[alias]` entries that shadow the external subcommands a declared step runs (`cargo fmt`, `cargo deny`, `cargo nextest`; cargo ignores an alias over a built-in command such as `build`, and warns that shadowing an external one is being phased out). The pass of a shadowed step is then the PR's to give. The control is the trust path: `**/.cargo/**` is a shipped trust-path glob (`assay-domain` `tiering/lists.rs`), so any alias change needs owner approval under rubric rule 4. In `gates-lint` the checkout is also verified against the fetched head tree (03 §2.1), so the alias is visible PR content; `gates-test` does not verify its checkout.
- *FIFO swap on a document read.* `exec::read_document` (and the local report store) checks the document path's type and then opens it in two calls; a process that left the gate's process group (`setsid`, the #154 family) could swap a FIFO in between and block the open. Closing it needs `O_NOFOLLOW | O_NONBLOCK`, which std cannot name without `libc`; the owner declined that dependency. The worst case is a hung job that its workflow timeout ends, which `decide` reads as `gate-error:job-failed`, so it fails closed. Revisit with #154.

## 4. Token and permission matrix

## 5. Secret handling

- OAuth token from `claude setup-token` in an environment (`assay-review`) available only to the `review` job of base-defined workflows. App keys (`ASSAY_VERDICT_PRIVATE_KEY`, `ASSAY_LEDGER_PRIVATE_KEY`) in `assay-publish`, available only to `open`, `admit`, `release`, `decide`, decide-only, `requeue`, `reconcile` and `report` of base-defined workflows (default-branch file, never a PR-merge-commit file).
- **Both environments use deployment branches "selected: default branch only"** (R3-04). This is what actually grants the secrets: ADR-20 and T20 decide which file a trigger runs, but without the policy a branch workflow (`on: push`, or `workflow_dispatch` dispatched against that branch) that names `environment: assay-publish` receives the App key. Every legitimate trigger runs with `GITHUB_REF` = the default branch, so the policy costs nothing. doctor asserts both policies in every consumer repo (§7).
- Rotation (`docs/operations/token-rotation.md`): expiry recorded at creation, as the non-secret variable `ASSAY_TOKEN_EXPIRES_ON` (`YYYY-MM-DD`, UTC) of `assay-review`, next to the secret (#93); `assay doctor` warns at T−30 days and fails from the recorded date on (`assay_app::token_expiry_warning`); the preflight's auth failures (`NotLoggedIn`, `AuthMethod`) link the runbook; a monthly canary workflow runs the preflight and fails loudly.
- assay never logs the environment; CLI debug output is off; uploaded artifacts are scanned for token-shaped strings (job fails if found): the token's windows (`03 §3`), a private key header, `sk-ant-`, and AWS key ids or long mixed runs the PR tree does not hold, in the raw bytes and in every JSON string decoded (`assay_app::EgressScan::scan_artifact`).

## 6. Prompt-injection posture (summary)

Defence in depth: *structure* (untrusted envelope, blind roles), *capability* (no Bash, no env, empty cwd, egress block), *validation* (schema, evidence, trigger, screens), *adjudication* (deterministic, models cannot approve), and *asymmetry* (an injection can at worst hide an LLM finding; it cannot forge a gate, a check, or an owner action). LLM review's contribution to the merge decision is advisory until measured (QA-05), so the blast radius of a successful injection is "a missed review", not "a bypassed gate".

## 7. Prerequisites enforced by `assay doctor` (NG2)

Read via the API at preflight and weekly; failures are loud and block LLM review of the repo until fixed:

- Ruleset on the default branch requires check `assay / verdict`, and on each other protected base `assay / verdict @<base>`, with the `assay-verdict` App `integration_id`; "require branches up to date" on; the bypass list holds **only the break-glass account** (a privileged identity, never the owner's daily account, R3-01). Every protected base's `[assay].digest` equals the default branch's (R3-27). A bare "required review on `.github/workflows`" is **not** sufficient: a feature-branch push can run its own workflow, which is why the check source, the artifact digests and the bundle pointer are all authenticated by the App and by output digests rather than by workflow-file protection.
- No assay workflow in the repository declares a trigger that runs the workflow file from a PR merge commit (`T20`).
- File-path restriction or required review on `.github/workflows/**`, `.assay/**`, `.claude/**`, `CODEOWNERS`, `.gitattributes`.
- Agent identity (`.assay/agents`) is not in `.assay/owners` or `approvers`, has no approval/bypass rights and no `issues: write` rights beyond comments; Actions may not create/approve PRs. An approver account exists (`H-13`, mandatory) and is not an agent; no id is in both `maintainers` and `owners ∪ approvers`. `H-08` is checked behaviourally in M1 in two parts: (a) agents push under agent ids; (b) from a cloud session and a local session, an attempt to comment and approve as each privileged id in a canary repo fails (R3-01).
- Where the plan supports push restrictions on the base, agent identities cannot merge into protected bases (optional; plan-dependent and unverified on Team, R3-03).
- Environments `assay-publish` and `assay-review` restrict deployment branches to the default branch only (T7, R3-04).
- Every job in the installed workflows that holds a secret or a write token carries the `github.run_attempt == 1` guard (T22, R3-05).
- Ledger repo (T23, R3-20): collaborators are the owner and the App only; a ruleset restricts `refs/heads/**` and file updates to the App; agent ids have no access.
- Environments, egress policy and pinned digests as above; actions in workflows pinned by SHA.
