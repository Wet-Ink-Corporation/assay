# 03 · Contracts

Status: **v1.2**. All contracts are versioned (`assay.<name>/<n>`), have a JSON Schema in `schemas/`, and are validated on read at every trust boundary (Z2/Z3 → Z4 especially). Unknown fields and unknown versions are rejected on untrusted input. Fields that identify or rank findings (`fp`, `group_id` for gates, `severity` of gate findings) are **never trusted from the producer**; Z4 computes or maps them.

## 1. Base configuration (`.assay/`, read from `base_sha`)

**Reserved plugin names** (#153). The rubric keys waivable rules by gate name (`rubric/v1.toml` `[[waivable]] gate = "temper"`, §2.1), so a built-in's name is reserved for that built-in: a plugin named `temper` whose adapter is not `builtin:temper`, or `weigh-in` whose adapter is not `builtin:weigh-in`, refuses the file (`ConfigError::ReservedName`), whatever the adapter (an unknown one included). A built-in may take another name; its findings are then never waivable.

**PR classes** (closed vocabulary used by `block_on_infra_for`, tiering and the approval rule): `trust-path` (a changed file matches the trust-path list, `04 §2.2`) and `exec-surface` (a change that adds or alters code which runs at build time: `build.rs`, proc-macro crates, build-dependencies, or a dependency package with a `custom-build` or `proc-macro` target or a changed `source`, `04 §2.2`). A PR may be both. `required_roles` and the run's tier are derived by `plan` and recomputed by Z4 (§4); they are not configuration.

Also in base: `.assay/owners` (TOML: `owners = [{id, login}]`, `approvers = [{id, login}]` and `maintainers = [{id, login}]`, numeric GitHub user ids are authoritative, logins are for display; `owners` and `approvers` list **privileged identities** only, accounts never authenticated in any agent-reachable context: the dedicated approver account that never pushes (`H-13`) and an optional break-glass account; `maintainers` lists the owner's daily account, which may author and push but takes no privileged action; R3-01, `H-06`), `.assay/agents` (TOML: `agents = [{id, login}]`, agent identities by numeric id; never owners). Both lists files (#58) are refused unparsed past 64 KiB and refused with any other key, a list of more than 64 entries, an id twice in one list, a missing list, a login that is not 1 to 39 ASCII letters, digits and hyphens not starting with a hyphen, an id in both `owners` and `approvers`, or an id in `maintainers` or `agents` that is also in `owners` ∪ `approvers`; one parser reads both files for every caller, `assay status` and `assay doctor` included (#305; doctor reports the last two cases as a failed `identity-lists` prerequisite rather than refusing the base); an absent file reads as empty lists, so nobody is eligible, and is never a default list. Then `.assay/exceptions.toml` (the only way a temper `ask` exception is accepted), `.assay/exceptions.toml` (the only way a temper `ask` exception is accepted), `.assay/suppress.toml` (rule ids and path globs to suppress), `.assay/globs.toml` (TOML: optional lists `risk`, `trust`, `exclude` and `docs` of path globs, each only added to the shipped list of that name in `04 §2`; any other key is refused, so no key can remove a shipped glob; globs use `*` within a segment, `**` as a whole segment and `{a,b}` within a segment, and `?`, `[`, `]`, `\` and `!` are reserved). Every one of these paths is itself a trust path. A skipped required gate is a `gate-error`, never a pass.

`.assay/exceptions.toml` (#63, #64) admits exactly four things, each with a non-empty `reason`; any other table or key, an empty reason, a `gate_config` key the gate-config diff does not compare (§2.1 step 3), a `base` or `head` that is not JSON, or a `test_inventory` or `manifest_switch` entry with neither blob or a blob that is not a git object id (40 or 64 lowercase hex digits) makes the file unreadable, which is a gate error. An absent file admits nothing.

```toml
[[exception]]                     # one temper `ask` exception (an `#[expect(lint, reason = ..)]`), by file and lint
path = "crates/x/src/lib.rs"      # as `temper scan` reports it, relative to the repository root
lint = "clippy::too_many_lines"   # the hit's `exception`
reason = "one state machine"

[[gate_config]]                   # one `.claude/temper.json` key changing from exactly `base` to exactly `head`
key = "gate"                      # one of the keys §2.1 step 3 compares
base = '{"allFeatures": true, "doc": true, "scan": true, "stepTimeoutSec": 900}'    # JSON, compared as a value; omitted when the key is absent at base
head = '{"allFeatures": true, "doc": true, "scan": true, "stepTimeoutSec": 1200}'   # JSON, compared as a value
reason = "the test job outgrew 15 minutes"

[[test_inventory]]                # every test-inventory loss of one file (§2.1 step 4a), between exactly these blobs
path = "crates/x/tests/it.rs"
base = "<git blob id at base>"    # omitted when the file is absent at base
head = "<git blob id at head>"    # omitted when the file is absent at head (a deletion)
reason = "two duplicate tests merged"

[[manifest_switch]]               # every manifest switch of one Cargo.toml (§2.1 step 4b), between exactly these blobs
path = "crates/x/Cargo.toml"
base = "<git blob id at base>"
head = "<git blob id at head>"
reason = "no doc examples in this crate"
```

A `test_inventory` or `manifest_switch` entry binds the file's exact (base blob, head blob) pair, which the finding's body quotes, so it admits that one change and cannot be replayed for a later one. A weakened lints table, a package that does not inherit the workspace lints and a manifest that does not parse are never admitted (§2.1 step 4).

An `[[exception]]` admits a hit by (file, lint). temper names only an `#[expect]`'s first lint, so the attribute's own hit is admitted only when every `#[expect]` starting on its line names exactly one lint and each is admitted in that file (§2.1 step 2). A `gate_config` entry binds the triple (key, base value, head value), not the key, so it cannot be replayed for a later change from another value; an entry without `base` admits only adding the key, and a removed key is never admitted.

## 2. Gate contract (adapter → assay)

A gate runs as a process from the manifest, cwd = the head checkout (or, in Z2s, a sanitised manifest-only copy), environment scrubbed to an allowlist (`PATH`, `HOME`, `CI`, `ASSAY_BASE_SHA`, `ASSAY_HEAD_SHA`, `ASSAY_RUN_KEY`, plus adapter-specific variables set by the adapter). It writes one `assay.findings/1` document to a file under the adapter's output directory and exits. For an `exec` gate that file is named by `ASSAY_FINDINGS_OUT` (always set by the adapter, overriding any inherited value), inside a directory created fresh for the run; the document's `source` must be `kind: "gate"` with `name` equal to the plugin's, and a path that is not a regular file is an invalid document:

| Exit | Meaning |
|---|---|
| 0 | Ran; the `conclusion` in the document is authoritative |
| 1 | Ran and failed the gate (document still expected) |
| ≥ 2, signal, timeout, or missing/invalid document | **Gate error** ⇒ `fail` (fail-closed), reason `gate-error:<detail>` |

### 2.1 The temper adapter (verified against temper's source)

What temper actually provides: `baseline --check [--base REF] [--locked] [--findings-out FILE]` (exit 0/1/2) which runs clippy, rustdoc and the scanner against `.claude/temper-baseline.json`, and writes `{temper_findings:1, findings:[{lint, rules[], severity: must|should|consider|unmapped, file, line, message, exception?}], ratchet:{…}}`. `--findings-out` must be under `target/` or `.temper/`. `temper gate` has **no** `--base`, `--locked` or `--findings-out`, mutates the tree without `--check`, and reads its base from `TEMPER_BASE`. An explicit `--base` takes precedence over `TEMPER_BASE`, and `--base origin/<x>` is a moving ref that fails with exit 2 when not fetched. `ratchet()` silently degrades to totals-only when `git diff` throws, in which case `raised` is skipped and `ok` can still be true.

The adapter therefore splits the work by what each step needs, because compilation is the only thing that must run hostile code:

**Z2s (`gates-static`, no PR-controlled execution)**
1. **`raised`**: JSON totals diff of `.claude/temper-baseline.json` at `base_sha` vs head. Any total that increases, or any new entry, is a failing finding. A diff in which every count only goes down is *not* a trust-path change (`04 §2.2`).
2. **`exception`**: the pinned `temper scan --all --json` (a pure source scan) run over the head tree; any finding carrying an `exception` (`ask`) that is not named in base `.assay/exceptions.toml` fails (temper downgrades `#[expect(..)]`-covered hits to `ask`, which its exit code ignores).
3. **Gate-config diff.** Compares `.claude/temper.json` at base and head key by key. The keys the gate reads are `GATE_CONFIG_KEYS = gate, scanner, manifests`; assay additionally compares `protected`, `review`, `skillGate`, `preapprovedDependencies` and `askOnNewDependency` as defence in depth (they steer hooks only). Any difference is a failing finding unless allowlisted in base. (`D-TEMPER-1` asks temper to expose this as a CLI subcommand so assay stops parsing a config file.)

   *As built (#63, `assay-gates` `TemperAdapter`, `gates-static` only).* Base and head trees are listed and read as blobs from the hardened object-only repository (§9), never from a checkout, under a cap on entries per listing and on bytes per read (100,000 and 32 MiB by default); past either the gate errors. The scan is `<node> <pinned>/temper.mjs scan --all --json`, where `<node>` is an absolute path (never looked up on `PATH`), `<pinned>` is the base pin's temper in its vendored layout (`temper.mjs`, `lib/`, `VERSION`), cwd is the head tree, and the environment is the §2 allowlist, whose `PATH` must hold only absolute entries, plus `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null` and `GIT_CEILING_DIRECTORIES=<the head tree's parent>`, under the plugin's `timeout_s` and a 16 MiB output cap; exit 0 or 1 (hard hits, which are `gates-lint`'s) is accepted, anything else is a gate error. Step 1 also compares the baseline's `crates` map: a crate added or mapped to another directory is a `raised` finding (it moves what the counts cover); removing one is allowed. A hit is an exception request when its `severity` is `ask` or it carries `exception`; `[[exception]]` entries (§1) admit it by `file` and lint, and an `expect-attr` hit only when the `#[expect]` attributes at its line, parsed from the head source, each name exactly one admitted lint. An `#[expect]` in the head's Rust that the scan did not report is an `exception` finding too. What the scan's walk cannot see fails as `blocker` `blind-spot` findings: a `.rs` file under a `target`, `node_modules`, `.git` or `.temper` directory at any depth; a submodule; a symlinked Rust file or `Cargo.toml`, and any other symlink that does not resolve lexically, inside the tree and through real directories only, to a regular file; a Rust file whose extension is not exactly `.rs`, or whose whole name is `.rs` (#177); a `.rs` file with an unterminated literal or comment, a character outside ASCII outside literals and comments, a token whose boundary depends on the edition (`cr"`, `cr#`, `'r#a'`, and a literal suffix, lifetime or raw identifier ending in `r` followed at once by `#` or `"`; boundaries follow edition 2021 and later, and these fail closed), a shebang line, or leading frontmatter; and, from a lexer over every head `.rs` file that normalises it as rustc does (byte order mark, CRLF) and ends tokens where `rustc_lexer` does (lifetimes, literal prefixes and suffixes, raw identifiers), a `cfg_attr(..)` whose arguments name `allow`, `expect`, `path` (raw or not) or a macro fragment (`$x`), an `allow`, `expect`, `warn`, `deny`, `forbid` or `cfg_attr` attribute not followed by `(`, an attribute named by a raw identifier (`#[r#allow]`), a `#` not followed by `[`, `! [` or `$`, an attribute whose path is a macro fragment (`#[$m]`, `#![$m]`), a macro fragment or open-ended repetition followed by `[`, `$`, `#` or `!` (`$hash $list`, `$m!`), the include macros named anywhere but in a `!` call, a `macro_rules` (raw or not) inside any bracket or another `macro_rules!` body, every `include!`, an `include_str!` or `include_bytes!` of anything but one literal, a `mod name;` in a `macro_rules!` body or inside any bracket (`(`, `[`, `{`), a top-level `mod name;` whose file is not a scanned `.rs` file of the head tree wherever rustc can look for it (crate roots are Cargo's conventional target files directly under a directory holding a `Cargo.toml` in the tree, a target directory's `main.rs` included; a root some `mod` could also make a module needs both placements), any `#[path ..]` or `#![path ..]`, and every plain `#[allow(` or `#![allow(` the scan did not report as an `allow-attr` hit at its file and line. Where rustc's reading cannot be modelled exactly, the checks refuse rather than model (Weigh-In default wi-b5affa). The baseline and `.claude/temper.json` must be present and parse on both sides, the scan output must parse, and the pinned copy must be readable; otherwise the gate errors (`gate-error:not-run`), never passes. The checks report `blocker` findings with rules `raised`, `exception`, `blind-spot` and `gate-config`. The PR's `.claude/temper/` is compared with the pinned copy by git blob id (changed, missing, extra, not a regular file), so none of its blobs is read: drift is one `major` `vendored-drift` finding that does not by itself fail the gate (T4); a PR with no vendored copy has none. PR-controlled names in titles and bodies sit in code spans, reduced to `[A-Za-z0-9_:-./]` with `://` replaced.
4. **Static checks implemented by assay**, because temper enforces them only in hooks on the author's machine (verified in `hooks.mjs`; `gate`/`baseline` ignore them): (a) *test inventory*: a `syn` parse counts `#[test]`-family attributes and `#[ignore]`/`cfg_attr(.., ignore)` at base and head; any decrease or new ignore fails unless allowlisted (`nextest list` totals from `gates-test` are recorded as an informational cross-check only: they require a build and come from a job that can lie); (b) *manifest switches*: `[lib] test=false`, `[[test]] test=false`, `autotests=false`, `doctest=false`, `harness=false`, `[patch]`, `[workspace] exclude`, `rust-version`, `edition` changes fail unless allowlisted; (c) *lints table diff*: `[lints]`/`[workspace.lints]` parsed as TOML at base and head, any weakening (level lowered, lint removed) fails; (d) *lint inheritance*: every workspace member manifest must carry `[lints] workspace = true`; a new member that omits it fails (this replicates the manifests step of `temper gate` that `baseline --check` does not run). All TOML is parsed in-process. Where a tool is needed (`temper scan`, `cargo metadata --locked --offline` for exec-surface detection) it is the **pinned base tool** running on a sanitised manifest-only copy with explicit `CARGO_HOME`, `RUSTUP_TOOLCHAIN` and `--config` flags and with `.cargo/config.toml`, `rust-toolchain.toml` and `.gitattributes` neutralised, never a binary or configuration from the PR tree.

   *As built (#64, `assay-gates` `TemperAdapter`, `gates-static`).* Base's tree is listed and its manifests and the Rust files head does not hold unchanged are read in one bounded batch; head's Rust and manifests come with step 2's read. Nothing is expanded, and where a reading is not certain the check fails closed (Weigh-In default wi-b5affa). (a) The inventory reads tokens from step 2's lexer, not a `syn` syntax tree, so a test inside a macro call (`proptest! { #[test] .. }`) counts; it compares per file, every `.rs` file whose blob differs. A test is an attribute whose last path segment holds `test` or is `bench` or `case` (`#[test]`, `#[tokio::test]`, `#[::core::prelude::v1::test]`, `#[r#test]`, `#[rstest]`, `#[test_case(..)]`), counted as unconditional when neither its own run of attributes nor any item around it (up to that item's first `;` outside brackets, or through its first `{ .. }`) holds a condition, and otherwise kept in a multiset keyed by the normalised text of those conditions, outermost first; an ignore is `#[ignore ..]` or any attribute naming `ignore` among its arguments (`cfg_attr(miri, ignore)`, `test_case(.. => ignore)`); a condition is a `cfg` other than exactly `cfg(test)`, or a `cfg_attr` naming `cfg` or a `$` fragment. A file fails `test-inventory` (blocker) when its unconditional tests drop, a conditional test's key disappears (the test is gone, or its conditions changed), its ignores rise, a condition is added on a `mod` or as an inner attribute (`#![cfg(any())]`), a top-level `mod name;` is dropped while a file it could name (`name.rs` or `name/mod.rs`, beside it or in the directory named after it) or a file below it that those files' own `mod` declarations reach at base (at most 1,000 files per dropped module and 64 MiB of work across one run, charged per visit and per byte of the places it queues, each base file counted once, past which it counts as tested), is still in head and held tests at base (or could not be counted or was not read there, or holds a module reference this check cannot follow by name), a `#[path]` module or a reference it cannot resolve is dropped, any `mod name;` is dropped from a file whose modules the reach scan cannot all place (a `#[path]` past its 64-attribute window, a `cfg_attr` naming `path`), its base text does not lex or was not read, or its head text asks for more than a fixed work budget (16 nested conditioned items, 1 MiB of condition text, item scans past 18 times its tokens); a deleted file is reported on the base side. A head file that does not lex (brackets nested more than 256 deep included) is step 2's `blind-spot`. A test a `macro_rules!` transcriber writes counts once per definition, not per call. (b) A `manifest-switch` (blocker) is any change, compared parsed and per target in file order, of `[patch]`, `[replace]`, `[workspace] exclude`, `members` and `default-members`, the presence of a `[workspace]` table, `package.workspace`, a removed path dependency (by table, name and path, `[target.<cfg>]` and `[workspace.dependencies]` included; a `workspace = true` dependency resolved through the root `Cargo.toml`'s `[workspace.dependencies]` of its side, and counted as a path dependency when that does not resolve it or does not own the manifest), a deleted package manifest, `rust-version` and `edition` (package, `[project]`, `[workspace.package]`, per target), the `auto*` discovery switches, and a target's `test`, `doctest`, `harness`, `required-features` and `path`; a new manifest is compared with an empty one, except that `edition.workspace = true` and `rust-version.workspace = true` are not changes and a new target's `required-features` and `path` are not either; a deleted manifest is compared with an empty one. (c) A `lints-table` finding (blocker, never admitted) is any entry of `[lints]` or `[workspace.lints]` that is removed, lowered (`allow` < `warn` < `deny` < `forbid`), given another priority or other keys (`check-cfg`), or not readable when it changed, and any entry added below `deny` (it can lower a lint a group set); removing the workspace manifest removes its lints. (d) A `lint-inheritance` finding (blocker, never admitted) is every head package manifest without `[lints] workspace = true` outside a directory the workspace manifest `exclude`s at both base and head; `members` globs are not modelled, since Cargo also makes path dependencies members. A manifest that is not UTF-8 TOML is `manifest-unreadable` (blocker, never admitted). `nextest list` totals are not compared: `gates-test` does not report them in any contract yet. For tiering, `assay_gates::compile_time_reach(revisions, revision)` (run for base and head; the plan use case that unions them into `ChangeSet` is not built yet) returns the include targets (`include!`, `include_str!`, `include_bytes!`, `#[path = ".."]`) of every Rust file and of every file one of them reads as Rust under another name (`include!("gen.txt")`, `#[path = "m.txt"]`), resolved from the file's directory, with `""`, which matches every path, for one it cannot place, for any symlink or submodule in the tree, for a `#[path]` in a file some `include!` reads, for an unparseable manifest, for a Cargo target `path` or `build` script that is not exactly `.rs`, and once the walk has resolved 10,000 distinct include literals; and the `include!`, `#[path]` and `mod` closure of every build script and proc-macro lib as `ExecRoot::Path`s (data a build script embeds is a root but not read as Rust), or `ExecRoot::Everything` for an unparseable or symlinked manifest, a symlinked entry, an unlexable file, a non-literal or escaped path, a path outside the repository or through a symlink, a `#[path]` not on a top-level `mod name;`, a `mod` in brackets or a macro body, a `mod` or `#[path]` in a file included inside brackets (`mod gen { include!(..) }`), an include in a macro body, a renamed include, a `cfg_attr` naming `path`, a macro-assembled attribute, more than 10,000 visits or entry points, a 100,000-unit work budget (spent before each file is queued) or 32 MiB of queued paths running out, a tree path or include literal past 4 KiB or 256 segments, a context past 32 directories, more than 32 MiB read on demand across the walk, or a reader that returns another number of blobs than it was asked for.

**Z2b-lint (`gates-lint`)**
5. Runs the **pinned** temper (not `.claude/temper/` from the PR) as `baseline --check --locked --base <base_sha> --findings-out target/temper/findings.json`, with `<base_sha>` the 40-hex SHA (never `origin/<base>`). Used for clippy and rustdoc `must/should/consider` counts. The adapter asserts `ratchet.mode == "diff+totals"`, that no ratchet note contains "only the totals", and that `ratchet.base` equals the merge-base of `base_sha` and `head_sha` as computed independently by assay (by `plan` in Z1 and published as its `merge_base` output, §4a; D4 A, #60); any mismatch is `gate-error:ratchet-degraded`. `raised` and `exception` entries in this document are unioned into the failures (they can only add), but their absence is never believed.
6. Severity mapping for display only: `must` → `blocker`, `should` → `major`, `consider` → `minor`, `unmapped` → `minor`. `evidence` is synthesised by the adapter from the head file at `file:line`; when the finding is on a deleted line it is read from base. The gate's pass/fail never depends on this mapping.

**Git attribute hygiene (replaces the v1 `.gitattributes` neutralisation, which did not work).** Neutralising attributes with `GIT_ATTR_NOSYSTEM` and an empty `core.attributesFile` leaves the in-tree `.gitattributes` in force, so `* -diff` still blinds temper's changed-line oracle, and GitHub-hosted images register `git-lfs` filters in the system gitconfig, so `* filter=lfs` collapses worktree files to pointers. The adapter and every Z1/Z2s/Z4 git operation instead **forbid**: `git check-attr --source <head_sha> diff text filter working-tree-encoding eol crlf ident` over **every changed path, both sides of each rename**, must report `unspecified` for all; any set, unset or value fails closed with `gate-error:gitattributes`. Scoping by extension does not work: `#[path = "evil.txt"] mod evil;`, `include!` and Cargo's `build = "build.txt"` make any file Rust, so `*.txt -diff` would hide Rust from the oracle. The only exception is a path matching a glob in base `.assay/plugins.toml` `[gates] binary_globs = [...]` (default empty; the glob dialect is `*`, `?`, and `**` / `**/` as whole path segments; read from `base_sha`, never head), meant for binary assets. An allowlisted path is **not silently admitted**: policing returns it in a separate `opaque` list, and downstream gates (the changed-line oracle, tiering, reviewer scoping) treat every opaque changed file as fully changed, because git may show it differently from its content. A NUL-byte "is it binary" check would not be a substitute: Rust string literals can carry NUL. Rust sources, `Cargo.toml`, `Cargo.lock`, `.cargo/*`, `.assay/*`, `rust-toolchain*`, `clippy.toml`, `.clippy.toml`, `rustfmt.toml`, `.rustfmt.toml`, `deny.toml`, `.claude/temper*.json` and `.gitattributes` itself can never be allowlisted, whatever the glob. Environment hygiene is in §9.

7. Declared steps (`[[plugin.step]]`) run in the named Z2b job under their own timeouts: `fmt` and `deny` in `gates-lint`, `tests` and `doctests` in `gates-test` (a different VM, so a hostile test can lie only about test results, and only a hostile `build.rs` or proc-macro can lie about clippy and ratchet counts, which is why those are the owner-approved exec surface). A repository's own `rust.yml` continues to run for developer feedback but is not trusted (a PR can edit it). `--no-tests=fail` closes the template's `--no-tests=pass` hole. This duplicates runner minutes (`06 §3` accounts for it).

   *As built (#66, `assay-gates` `TemperAdapter`, `gates-lint`).* The adapter takes the base SHA and the merge base as `RatchetBase` (without one `gates-lint` is a gate error before anything runs). Since #60 ST-5 (D4 A) the merge base is computed once, by `plan` in Z1, and published as its `merge_base` output (§4a); since #60 ST-8 `assay gate gates-lint` takes it from `ASSAY_MERGE_BASE` (below). It runs each `lint` step in file order under its own `timeout_s` first, before any build script or proc-macro has run in the tree, then removes any stale `target/temper/findings.json` from the head tree (refusing a symlink at `target` or `target/temper`), then runs step 5 from the head tree with the Z2s environment under the plugin's `timeout_s`. A `lint` step a signal ended is run once more, whose termination decides, under the same infra-class rule as `gates-test` (below; #229); `baseline --check` is never retried. A run that does not exit (a step after that retry), or a `baseline --check` exit other than 0 or 1, is that `gate-error` (`timeout`, `signal`, `output-too-large`, `exit-N`); a step that exits non-zero fails the gate. The document is read as a regular file of at most 64 MiB, parsed once with repeated keys refused, and every object is closed to temper 1.3.0's fields, severities and tools; anything else, a `ratchet.ok` that is not exactly "no `new_code`, `increases` or `errors`", or an exit code that disagrees with `ratchet.ok`, is `gate-error:not-run`. A `ratchet.mode` other than `diff+totals` (`totals`, `strict` and any unknown mode), a note containing "only the totals", or a `ratchet.base` other than the merge base is `gate-error:ratchet-degraded` (the `GateRunner` port's `gate_error`). `raised` entries fail as Z2s `raised` findings, each at a synthesised spot in the baseline (at most 1,000 reported; the gate fails on any); an `exception` entry fails unless base `[[exception]]` admits its (file, lint), since Z2s step 2 already holds the stricter check and failing every admitted `#[expect]` would refuse what base approved. Display findings (step 6): changed-line findings, counts above the baseline and located compile errors, at most 1,000, with evidence read through the object-only repository (from base only for a file head does not hold), never from the checkout a build script could rewrite, within 16 MiB of cited blobs. Their rules are the lint names, prefixed `lint:` if one ever equals a waivable rule.

   *As built (#67, `assay-gates` `TemperAdapter`, `gates-test`).* The adapter runs each `test` step in file order from the head tree with the §2 environment, under its own `timeout_s` and a 16 MiB output cap, and reads nothing back: no document, no `nextest list`. A step that exits non-zero fails the gate and the next step still runs; with `--no-tests=fail`, nextest exits non-zero (4) when no test runs, so zero tests fail. A step a signal ended (not one it exited from: a crashing test is the test runner's own non-zero exit) is the only infra-class outcome (06 F9) and is run once more, whose termination decides; an exit code (cargo exits 101 for a registry failure and a compile error alike), a timeout, an output cap or a step the supervisor cannot run is never retried. A step that does not exit, after that retry, ends the run as `gate-error:timeout`, `signal` or `output-too-large`; one that cannot run is `gate-error:not-run`. A temper plugin with no `test` step is refused there (`gate-error:not-run`; `run_gates` does not schedule it). `gates-test` needs no `RatchetBase` and never runs temper. Base config refuses any declared step argument `--no-tests` or `--no-tests=<x>` other than exactly `--no-tests=fail` (`ConfigError::NoTests`), whatever its job, and refuses a `test` step that runs nextest (a program named `cargo-nextest`, or a `nextest` argument) without `--no-tests=fail` before any `--` (`ConfigError::NoTestsFailMissing`, #229), so zero tests never fall back to nextest's default. A step that runs nextest through a wrapper script or a cargo alias (`cargo nt`) is not recognised; only its exit code is read. The `lint` steps in `gates-lint` get the same single retry on a signal (#229).

   *As built (#67, `assay gate`, `crates/assay-cli/src/gate.rs`).* A gates job runs `assay gate <gates-static|gates-lint|gates-test> --config <base plugins.toml> --head <head checkout> --out <dir>` with `ASSAY_RUN_KEY` set (non-empty; the documents' `run_key`). All three run. `gates-static` (#60 ST-7, `crates/assay-cli/src/gate/static_job.rs`) also takes `--node <abs> --temper <abs>`, `--temper` being the pinned temper copy the workflow prepared from the base's `oci:sha256:` pin (D8 A); both must be absolute as given and resolve outside the head tree. Before anything runs it also requires `ASSAY_BASE_SHA` and `ASSAY_HEAD_SHA` (40 lowercase hex), `ASSAY_RUN_TOKEN`, `GITHUB_REPOSITORY` and `PATH`, each named and never echoed; it then fetches base and head by SHA into an object-only repository (§9) in a scratch directory from `https://github.com/<repo>.git`, authenticated with `ASSAY_RUN_TOKEN` and no other token (no gate sees it), and runs the temper and Weigh-In plugins through `run_gates` over it (steps 1-4 above, the scan from the head tree); its documents, stdout lines, output and exit codes are those of `gates-test` below. A pinned commit that cannot be fetched is exit 2 before any gate runs, with nothing written. The workflow must check out `ASSAY_HEAD_SHA` into `--head`: `gates-static` does not verify that the checkout is that commit (`gates-lint` does, below). Z2s fails closed through its cross-check of the scan against the fetched head (step 2): an `#[expect]` or `allow` the fetched head holds that the scan of the checkout did not report fails as `exception` or `blind-spot`, and a scan hit base does not admit fails as `exception`. `gates-lint` (#60 ST-8, `crates/assay-cli/src/gate/lint_job.rs`) takes the same `--node`, `--temper` and variables, plus `ASSAY_MERGE_BASE` (plan's `merge_base`, 40 lowercase hex), each refused by name and never echoed before anything runs; `ASSAY_BASE_SHA` and the merge base are its `RatchetBase`. It fetches base and head as `gates-static` does (the same code, `gate/fetch.rs`). Because its steps run PR-controlled code, it then refuses, with exit 2, no gate run and nothing written, a `--head` checkout that is not exactly `ASSAY_HEAD_SHA`'s tree (#348, `gate/checkout.rs`): every entry of the fetched head tree must be there as the same kind (a regular file with the same owner execute bit and the bytes of its blob as the object-only repository holds it, with no attribute, filter or `eol` applied, so a smudged or converted file is refused; a symlink with the same target, never followed; a submodule as an empty directory), and nothing else that is not a directory may be, untracked and ignored files included, except the checkout's own `.git` at its root and an untracked `target/` directory at its root (where the warm `target/` is restored, ADR-21); a name that is not UTF-8 is refused as untracked. The walk reads each directory lazily and counts every entry as it is read, before its metadata: files, symlinks and submodule directories against the tree listing's entry cap (which counts the same kinds), directories against every directory the tree implies plus 1,024 untracked ones; the blob reads are bounded by the listing's byte cap. The untracked root `target/` is not examined: whatever the workflow restored there (the warm `target/`, or anything left from another commit: prebuilt dependencies, fingerprints) is believed and may be loaded by cargo, a residual of ADR-21's restore that this check does not close. The checkout is verified rather than replaced by an export of the fetched tree because temper's changed-line diff runs in the checkout's own git (the merge base of `--base` and `HEAD`, and the working tree against it), which an export would lack, so the ratchet would always degrade; the merge base temper reports is believed only when it equals `ASSAY_MERGE_BASE` (step 5), so the checkout's history must hold the base. It then runs temper's `lint` steps and `baseline --check` (steps 5-7, through `TemperAdapter`, its evidence read from the object-only repository) and each `exec` gate whose `job` is `lint`, all in the checkout with the §2 environment (no token, no `ASSAY_MERGE_BASE`); its documents, stdout lines, output and exit codes are those of `gates-test` below. Residuals: the checkout's `.git` is the workflow's and is not compared, and once the verification passed a build script can rewrite anything the job's user can, the object-only repository included (05 T6). In `gates-test` it runs every plugin base config schedules there through `run_gates`: the temper plugin's `test` steps through `assay_gates::TemperTestAdapter`, which holds only the head tree, the §2 environment and the run key (no `node`, no pinned temper, no object-only repository, no `RatchetBase`), so the job takes nothing from `gates-lint`, and each `exec` gate whose `job` is `test` through the exec adapter, its document under a scratch directory. Before anything runs it refuses (exit 2) a usage error, a missing run key, a head that is not a directory, a config that is not a regular file outside the head tree (paths compared with symlinks resolved; base config never comes from the PR, 05 T3), and an `--out` that exists in any form, sits inside the head tree, has no directory as its parent, or whose parent is not written as its resolved path (a symlink or `..` on the way is refused rather than followed, since a test could retarget a symlink before the writes); the head tree, config and `--out` are then used by their resolved paths, so the git ceiling (the head's parent) is above the tree. After the gates ran it creates `--out` (refusing one that appeared meanwhile, so nothing a test wrote before the gates finished is in it; a process that escaped its group with `setsid` is 05 T6's accepted residual) and writes each concluded gate's validated document, compact, as `<out>/<plugin>.json` through a dot-named temporary file that is persisted without replacing anything; a gate error writes nothing. stdout gets one line per scheduled gate in file order, `<plugin> <pass|fail|neutral|gate-error:<detail>>`, which is what the job's outputs report beside each document's sha256 (`decide`'s `ReportedGate`), and stderr gets each gate error's cause. The exit code is 0 once the lines and documents are written, whatever the gates concluded (the documents and lines speak), and 2 when the job cannot run, a document cannot be written or the scratch directory cannot be removed.

**What the adapter owes `decide` (rubric v1 waive, `04 §5`).** The human-decision findings of the Z2s steps carry these rule ids, and only these are waivable (`rubric/v1.toml` `[[waivable]]`, keyed by gate and rule): `raised` (a raised baseline, step 1), `exception` (an `ask` exception not in `.assay/exceptions.toml`, step 2), `gate-config` (gate-config drift, step 3), `test-inventory` (a test-inventory decrease or new ignore, step 4a) and `manifest-switch` (a manifest switch, step 4b). Every other finding (clippy, rustdoc, lints-table weakening, lint inheritance, build, tests, deny) uses any other rule id and is never waivable. A waiver names a fingerprint, and `decide` applies it all or nothing: only when every gate finding carrying that fingerprint, in any gate, has a rule listed for its own gate. Otherwise it clears none of them, so a fingerprint shared with a non-waivable finding is never half-waived. A failure cause with no finding of its own (a failed declared step such as `fmt`, `deny`, `tests` or `doctests`, or any failure the adapter cannot attribute to a finding) must never be hidden by waiving the gate's findings, so `decide` clears a failed gate only when the gate's step attribution is *known and empty*: the adapter attested that every failure cause is a finding. Attribution is *unknown* unless a contract carries it, and **no contract does yet**: `assay.findings/1` has no step results. Until the gate findings contract carries step results, waivers therefore cannot clear a failed gate (they are still recorded against the findings they name). Adding that carrier (a schema change to `assay.findings/1` or the gate report) is a later H-16 schema decision for the temper adapter story.

**What the snapshot owes `decide` (rubric v1 rule 8, `04 §2.4`).** `decide`'s `readiness` is the PR's draft flag from Z4's GitHub state snapshot taken at decide time (`04 §5` inputs). It is independent of the plan's `draft` (§4), which is what yields an LLM stage that did not run because the PR was a draft. `decide` excuses that stage only while the snapshot still says draft. Once the snapshot reads ready on a `full`, `lite` or `micro` PR, the stage is read as `infra-llm-unavailable`. A decide-only re-decision must therefore take `readiness` from a fresh snapshot, never from the evidence run's plan or an earlier snapshot. Otherwise a PR marked ready after its run would keep its draft excuse.

### 2.2 The Weigh-In adapter

Specified in `04 §9`; it consumes `weighin ci-check --json` (a versioned contract requested from Weigh-In, `D-WI`). Until that exists the adapter runs in `experimental` mode, non-required, using journals and atoms only.

*As built (#109, `assay-gates` `WeighInAdapter`, `gates-static`, experimental).* A required `weigh-in` plugin is refused (`gate-error:not-run`), since this mode never fails. The adapter reads the head tree only, through the object-only repository, from one listing of `.kb`; a file, symlink or submodule at `.kb`, `.kb/_ledger`, `.kb/_intake` or either directory below is a `weigh-in-unreadable` finding, never an empty ledger. It reads the regular `*.jsonl` files directly under `.kb/_ledger/journal/` and `*.md` directly under `.kb/_intake/decisions/`, at most 10,000 files and 16 MiB by listed size before anything is read. A journal line is one JSON object (repeated keys refused) whose `type` is one of `item_raised`, `item_triaged`, `item_grounded`, `item_presented`, `item_deferred`, `item_decided`, `item_defaulted`, `item_dismissed`, `record_written`, whose `item_id` is exactly `wi-[0-9a-f]{4,16}` (`docs/decisions/0003`) and whose `ts` is `YYYY-MM-DDTHH:MM:SSZ`; beyond those only `item_raised.blocks` and `item_triaged.door`/`authority` are read. An atom is read only for its front matter's single `weighin_item: "<id>"` and must be named `<id>-<slug>.md`. A file not exactly in that form is refused whole as a `weigh-in-unreadable` finding (wi-b5affa). Events are folded in (`ts`, journal path, line) order; the last status event decides an item's status, the last triage its door and authority, the last raise its `blocks` (absent is unknown, never none). Every item open at head is reported, not only the PR's: 04 §9 rule 1's blocking set as `weigh-in-open-blocking` (`major`; a door other than `two-way` or an authority other than `judgment` blocks, so an unknown value fails closed) and its pending-triage set as `weigh-in-pending-triage` (`minor`), at most 1,000 findings and a `weigh-in-truncated` note. The document concludes `pass` when it reports nothing and `neutral` otherwise, never `fail`; each finding and the `assay / gate: weigh-in` check summary say that G2 is enforced by CP1 and convention until D-WI. Rules 2, 3 and 5 and commit trailers are not checked in this mode.

## 3. Findings (`assay.findings/1`)

```json
{
  "schema": "assay.findings/1",
  "source": {"kind":"gate|reviewer","name":"temper","version":"git:<sha>","role":"bugs","run_key":"…"},
  "conclusion": "pass|fail|neutral",        // gates only; reviewers have no conclusion field
  "findings": [{
    "class": "logic|error-handling|concurrency|resource|security|api-design|layering|tests|docs|compliance|deps",
    "rule": "ERR-04",                        // gate: plugin rule id; reviewer: optional rule-id citation
    "kind": "defect|omission",               // omission: nothing to quote; anchor on enclosing function
    "severity": "blocker|major|minor|nit",   // reviewers: operational definitions in 04 §3
    "introduced_by": "diff|interaction",     // interaction: names changed symbol + unchanged affected caller
    "pre_existing": false,                   // claim; Z4 verifies against the diff
    "file": "crates/x/src/lib.rs", "line": 88, "end_line": 91, "side": "RIGHT|LEFT",
    "evidence": "let x = y.unwrap();",       // verbatim span, ≤ 400 chars; for omission: the function signature
    "expected_behavior": "…",                // required for kind=omission, ≤ 300 chars
    "trigger": "request with empty body reaches line 88 via handler::parse", // required for major+, ≤ 300
    "caller": {"file":"…","line":12,"evidence":"…"},   // required when introduced_by=interaction
    "title": "…",                            // ≤ 100, plain text
    "body": "…",                             // ≤ 1,200, restricted markdown (04 §6)
    "fix": "…",                              // ≤ 600, optional; fences with info string `suggestion` are stripped
    "confidence": "high|medium|low",
    "group_hint": "short root-cause label"   // the coordinator assigns the authoritative group_id
  }],
  "stats": {"files_read": 12}
}
```

- **No producer-supplied `fp`.** Z4 computes `fp = sha256(class ‖ file_at_head (rename-resolved) ‖ enclosing_symbol ‖ norm(first line of evidence with content) [‖ norm(expected_behavior), kind=omission only] ‖ occurrence_index)[..8 bytes]`, where `norm` is the single shared normaliser (collapse whitespace, unify quote styles, strip trailing comments, treat `…`/`...` as wildcard) also used by the evidence check, a line with content is neither blank nor only wildcards, each `‖` field is length-prefixed so no boundary can move, `expected_behavior` keeps two omissions in one function apart (Weigh-In wi-f39f2e), and `occurrence_index` disambiguates identical evidence within a file/symbol. `class` is a closed enum, so two runs that describe the same defect in different words still collide on purpose. Dismissals match fuzzily: same file, same enclosing symbol, similarity ≥ 0.8 of the whole normalised evidence (and of the normalised `expected_behavior` for an omission; evidence with no line of content matches nothing), **and** the same `class` with severity ≤ the dismissed severity; a fuzzy match of higher severity is published with the note "previously dismissed similar (<severity>)" (R3-25). Fingerprints are authoritative only when computed by Z4; Z3 runs the same pure function non-authoritatively, solely to apply `admit`'s suppress and dismissal lists before spending verifier budget (`04 §4` step 6).
- Reviewer findings carry no `conclusion`; a reviewer cannot say "approve".
- Hard length caps are in the schema; over-length input is rejected, not truncated.
- **Free-text egress scan** (T2, T8): in Z3 the assay process, and again in Z4, drop-and-flag any finding whose `title`, `body`, `fix`, `trigger` or `evidence` contains the OAuth token or its common encodings (normalised by stripping non-alphanumerics and comparing windows of ≥ 12 characters, plus base64 and hex forms), or any alphanumeric run ≥ 20 characters that occurs in neither the PR tree nor the base REVIEW.md. Any hit fails the `review` job, raises `injection-suspect` and flags token rotation. Precisely (#87): a window is 12 characters of the token, of its base64 at each of the three alignments, or of its hex, compared after folding (invisible characters dropped, lookalike letters read as Latin, lowercase) and keeping ASCII letters and digits only, so both base64 alphabets and both hex cases match; hex written one byte at a time behind `0x`, `\x`, `\u00`, `U+00`, `&#x` or `%`, or as decimal references, is read as hex too; characters drawn like one ASCII letter or digit are read as it from a generated table (canonical and compatibility decompositions, Latin letter names, decimal digits and the single-character skeletons of Unicode 15.1 `confusables.txt`, except the ambiguous `l` and `O`), any other non-ASCII alphanumeric is a wildcard that matches any token symbol, a window with wildcards matching only with at least 7 other symbols (9 in the hex view), so lookalikes of any script cannot hide the token while ordinary non-ASCII prose passes; numeric and letter-like symbols the table cannot read (`½`, `⑳`, `Ⅻ`) are refused outright; octal escapes and decimal byte lists are an accepted residual risk of T2 (no view decodes them); the run's own base and head commit ids are explained; a run counts invisible characters, and occurs in the tree only as a whole run of the indexed texts (at most 64 MiB, refused past it); every field the reviewer wrote is scanned, before any other validation step and past the findings cap. Z4 holds no token and applies the run rule only.
- Display mapping: `blocker` → 🔴, `major` → 🟡, `minor`/`nit` → 🟡 (nit), `pre_existing` → 🟣.

## 4. Run description (`assay.run/1`)

`{run_key=evidence_key, run_uid=(repo_id, run_id, run_attempt), repo, pr, base_sha, head_sha, base_ref, tier, tier_reasons[], classes[trust-path|exec-surface], roles[], required_roles[], shards[], plugins[{name,required,pin|job,steps[{name,job,timeout_s}]}], trust_paths_changed[], exec_surface_changed[], filtered_stats:{files, lines, excluded[]}, artifact_names:{…per-job nonce…}, draft:bool}`. `tier` is any row of 04 §2.3, `needs-split` included. A built-in gate carries its `pin`; an `exec` gate has none and carries the Z2b `job` it runs in instead. `plan` names each consuming job's artifact `assay-<job>-<nonce>` with a fresh 128-bit nonce per job (`plan`, `gates-static`, `gates-lint`, `gates-test`, `admit`, `review`, `decide`), and refuses a repeated nonce. A draft gets `roles: []` and no shards (gates only, 04 §2.4) but keeps the `required_roles` of its tier. Otherwise `plan` writes one shard of every reviewed file: it holds neither the context pack nor the import graph, so the split by dependency cluster (04 §3) is made where the pack is built, by `review`, and `shards` is not a list of the shards that ran. `run_key` is the evidence key of 02 §3, `sha256:<hex>` over its fields, each length-prefixed, with `config_hash` over every file of base `.assay/`. `budget:{ledger_day_spent_aeu, day_cap_aeu, window_state, allowed, slot, deferral: none|budget-deferred|slot-busy, tier_degraded_from?, reused_evidence?, retry_grant?}` is added by `admit`, not `plan`, and carried in `admit`'s outputs. Informational for Z3; **recomputed by Z4** (including `classes`, `tier`, `required_roles`), except that Z4 accepts `admit`'s full→lite degrade (`tier_degraded_from`) when recomputing required roles, so a degraded run does not read as a missing role (R3-27). `tier_degraded_from` is set only on a run degraded from `full`, so its `tier` is `lite`. `run_uid` keys leases, ledger records and the pending stamp; `evidence_key` is for reuse only (R3-16).

`admit` (#72) reads the budget twice: before it waits for a slot, and again once it holds one, with its own lease left out, so reservations made during the wait count (R3-27); a run the second read defers releases its slot by compare-and-set and is `budget-deferred`. The run never reserves more than its lease's `reserved_aeu` (#300): a second price above it spends at the price the lease was taken for while that still fits (its tier, degrade and grant; a grant recorded during the wait stays waiting), and otherwise the slot is released by compare-and-set and the run is `slot-busy` with `allowed: true` (06 §1). It refuses a re-run (attempt other than 1), a plan document that already carries `budget`, one of another `run_uid`, and a non-draft one whose `roles` are not its `required_roles`. A draft, `trivial` or `needs-split` run gets no `budget` and reads no ledger: its document passes through unchanged. Otherwise: `ledger_day_spent_aeu` and `day_cap_aeu` (40) are AEU as JSON numbers; `window_state` is `unobserved` until the rate-limit window is read (06 §1); `allowed` is whether the budget gate passed, so `false` on reuse and on `budget-deferred` and `true` on `slot-busy`; `slot` is `slot-N`, or null when no slot was taken; `reused_evidence` is the ledger's `complete` evidence record for this `run_key` at a tier at least the plan's (a draft, deferred or degraded record never stands in); `retry_grant` is the waiting grant `admit` consumed. A degraded document has `tier: lite` and `roles: [combined]`, keeping `required_roles` and `tier_reasons`. The document is revalidated as `assay.run/1` before it is written.

## 4a. Job outputs (unversioned, trusted channel)

Each pipeline job writes its outputs to the file `GITHUB_OUTPUT` names, and every later job reads its upstream jobs' through exactly one input, `ASSAY_NEEDS: ${{ toJSON(needs) }}` (D10 A, #60). The channel is GitHub's and assay's own, so it carries no schema id and no version: producer and consumer are one build, one encode/decode pair per job in `assay-cli`'s `outputs` module, round-trip tested. It is read as strictly as a contract (wi-b5affa, I6).

- **Writing.** One `name=value` line per output, appended in one write; names come from a closed set per job (`OutputName`); a value holding `\n` or `\r` is refused before anything is written, so no value can forge a second line or a `name<<delimiter` block (I5). A write that fails fails the command with exit 2; no partial-output contract is promised.
- **Reading `ASSAY_NEEDS`.** At most 256 KiB, else refused unparsed. One JSON object without repeated keys, holding exactly the jobs the reading command needs (no other, none missing), each exactly `{"result": "success"|"failure"|"cancelled"|"skipped", "outputs": {<name>: <string>}}`. An output a job does not write, a required one absent, or a value that does not parse is refused. An empty value reads as not written (GitHub's value for an unset output).
- **`guard`'s outputs** (the run identity, I2): `run` (`true`; a `false` run writes nothing else and no job needs it), `pr`, `head_sha`, `base_sha` (40 lowercase hex), `base_ref`, `draft` (`true`|`false`), `author_id`, `sender_id` (positive decimal, no leading zero), `trigger` (`opened`|`synchronize`|`reopened`|`ready_for_review`|`edited`|`workflow_dispatch`), `before` (for `synchronize` only, and required there) and `default_branch`. Branch names are non-empty with no control character. The identity is read only from a `guard` whose result is `success`. A push's `forced` is not an output: `open` determines it.
- **`guard`'s decision** (#60 ST-2, 0006): a payload whose `repository.id` is not `GITHUB_REPOSITORY_ID` cannot run (exit 2). A PR whose head repository is not this one, or is deleted, is refused with exit 1 and nothing written, for every action (checked before the `edited` filter); so is a `workflow_dispatch` for a closed PR, whose identity is read from the PR (`ASSAY_RUN_TOKEN`, the only token `guard` reads) with its `sender` and `default_branch` from the payload and `trigger: workflow_dispatch`. An `edited` without a base change writes `run=false` alone (exit 0); any other accepted event writes `run=true` and the identity (exit 0).
- **The run** comes from `GITHUB_RUN_ID`, `GITHUB_RUN_ATTEMPT`, `GITHUB_REPOSITORY_ID` (positive decimal, no leading zero: `01` is refused, not read as 1) and `GITHUB_REPOSITORY` (`owner/name`); a variable that is missing or does not parse is named and never echoed. A command holding a write token refuses any attempt but `1`, an unset one included, before it reads a token (R3-05, I1).
- **The event payload** (`GITHUB_EVENT_PATH`, read by `guard` only, at most 8 MiB, no repeated key): a `pull_request_target` `opened`, `synchronize` (with `before`, and `after` equal to the head), `reopened`, `ready_for_review` or `edited` (`changes` required; a base change only when `changes.base` is an object, absent meaning none and a present `null` refused), or a `workflow_dispatch` whose only input is `pr` (positive decimal). Any other action (`labeled` included) and any other dispatch input (role, cap, factor: R3-14) is refused. A head repository other than the base, or one GitHub reports deleted, is reported to `guard`, never dropped (0006).
- **`plan`'s outputs** (#60 ST-5, D4 A): `assay plan --out <dir>` plans guard's identity (`ASSAY_NEEDS` holding `guard` only) into `<dir>/run.json`, the plan artifact's only file, and appends, in this order: `run_digest` (`sha256:<hex>` of the exact bytes of `run.json`), `run_key` (the document's), `tier` (§4's codes), `draft` (`true`|`false`, guard's), `review` (`true` exactly when the PR is not a draft and its tier has an LLM stage, so `false` for `trivial` and `needs-split`), `merge_base` (git's merge base of the pinned `base_sha` and `head_sha`, 40 lowercase hex, the ratchet base `gates-lint` takes; commits with no common history are refused), and one `artifact_<job>` per artifact job (`artifact_plan`, `artifact_gates_static`, `artifact_gates_lint`, `artifact_gates_test`, `artifact_admit`, `artifact_review`, `artifact_decide`), each the document's `artifact_names` entry, `assay-<job>-<32 lowercase hex>`. The plan request has no package sets (D2 B: every Rust change is exec surface) and no include-target scan, and the prompt bundle hash is the embedded bundle's, as for `check --local`. GitHub's file list is read through `gh`, and the pinned commits are fetched into an object-only repository in a scratch directory, both with `ASSAY_RUN_TOKEN` (the job's `github.token`, `contents: read`, `pull-requests: read`) and no other token; a REST list git does not confirm is `PlanError::FileList`. Before the network it refuses (exit 2) a usage error, the run variables, a `GITHUB_OUTPUT` that is not a regular file (never created), the needs, a missing or invalid token, and an `--out` that exists in any form, has no name, has a parent not written as its resolved path, or sits inside a checkout (an ancestor holding `.git`). `--out` is created only once the document is ready (one that appeared meanwhile is refused), and the outputs are appended after the document, so a run that cannot write it writes no output. Exit 0 once both are written, 2 otherwise; stdout gets one line naming the document, its digest, the tier and `review`. `plan` holds no write token, so it does not refuse a re-run attempt. Its outputs are read only from a `plan` whose result is `success`; every one is required, and a `review` that contradicts `tier` and `draft` is refused.
- **The gate jobs' output** (#60 ST-6, ST-7, ST-8; `gates-test`, `gates-static` and `gates-lint` write it): `gates`, one compact JSON array with one entry per plugin the job ran, in file order, `{"plugin":"temper","conclusion":"pass","sha256":"sha256:<hex>"}` for a gate that concluded (`pass`, `fail` or `neutral`, and the sha256 of the exact bytes of the `<plugin>.json` it uploaded) or `{"plugin":"x","error":"gate-error:timeout"}` for a gate error (its reason, §5's `gate-error:<detail>`); `[]` when nothing is scheduled. A plugin that is not a plugin name is not encoded and the job exits 2 with nothing written; every document and the output are encoded before anything is written, and the output is appended after the documents, so a job that cannot write its documents writes no output. `GITHUB_OUTPUT` is required: unset, missing or not a regular file is exit 2 before any gate runs. It is read only from a gates job whose result is `success`, `gates` its only output and required; anything but exactly that shape (each entry exactly those keys, no repeated key, a gate error's reason exactly as assay writes it, `exit-3` never `exit-03`) is refused.
- **`open`'s inputs** (#60 ST-4; it writes no output): `ASSAY_NEEDS` holding exactly `guard`, read as above; `--config`, base `.assay/plugins.toml`, whose `[assay].ledger_repo` is required (D3 A); `ASSAY_GITHUB_TOKEN` (the `assay-verdict` App's: `checks: write`, and `contents: read` for a `synchronize`'s compare; the run's `created_at` is read with it too, which on a private repository needs `actions: read`), `ASSAY_LEDGER_TOKEN` (the `assay-ledger-writer` App's) and `ASSAY_VERDICT_APP_ID`/`ASSAY_VERDICT_BOT_ID` (the App's check is found by app id). Each is named and never echoed when missing or invalid, and all are read after the first-attempt refusal and before any call. A push's `forced` is `GET compare/<before>...<head>` (`behind` or `diverged`), and the record's `at` is the run's `created_at`, never the job's clock.

- **The review job's outputs** (#60 ST-9, D11 A): until the real review (M2), `assay review --placeholder` writes exactly `stage=not-run`, `cost_aeu=0` and `documents=[]`, so `decide` applies the LLM-unavailable policy. Any other argument is a usage error (exit 2) and writes nothing; `GITHUB_OUTPUT` is opened as for `guard` (a regular file, never created; anything else is exit 2). It reads no secret.

- **`admit`'s slot and `release`** (#60 ST-10, 06 §1, 04 §1 S10): admit's outputs are the closed set `admission`, `deferral`, `slot`, `lease_commit`, `reserved_aeu`, `tier`, `degrade`, `run_digest`, `pack_digest`, `review` (#60 ST-11 writes them). `slot` is the held slot's index (`0` or `1`) and `lease_commit` the 40-hex commit its ref points at, written together only when admit holds a slot; either without the other, or any other spelling, is refused. They are read whatever admit's result, since admit writes them once it holds the slot and has written the reservation. `assay release --config <plugins-toml>` reads `ASSAY_NEEDS` holding exactly `admit` and `review` and refuses any attempt but `1` before it reads `ASSAY_LEDGER_TOKEN`; with no `slot` it exits 0 with no config, token or port read. Otherwise it reads the run's `reserved` cost record (none: exit 2, nothing written), releases the slot by compare-and-set on `lease_commit` (a lease reaped since is reported and nothing deleted), then appends the `final` record with the reservation's identity: at the review's `cost_aeu` with no roles when the review job's result is `success`, else at the reservation (the run cap, with its roles), `cancelled` true only for a `cancelled` review (§6c). A `final` record already there is reported and nothing is written. The review's outputs are read only from a `success` review: exactly `stage` (`not-run` until M2), `cost_aeu` (AEU as the ledger writes it, §6c) and `documents` (exactly `[]` until M2), each required. `release` writes no output; exit 0 once settled, 2 when it cannot run or settle.

- **`admit`'s outputs** (#60 ST-11, 04 §1 S1a, D6 A): `assay admit --config <plugins-toml> --artifacts <dir> --out <dir>` reads `ASSAY_NEEDS` holding exactly `guard` and `plan`, refuses any attempt but `1` before it reads a token, and reads plan's `run.json` from `<artifacts>/<artifact_plan>/` (a regular file, no symlink, at most 8 MiB), whose sha256 must equal plan's `run_digest` before anything else is read (a mismatch is exit 2, no slot taken). Then it reads `[assay].ledger_repo` and `ASSAY_LEDGER_TOKEN`, `ASSAY_GITHUB_TOKEN` (the App's: command comments) and `ASSAY_RUN_TOKEN` (the pinned commits, the range's commit identities, the previous run's bundle). A run with no LLM stage (a draft, `trivial`, `needs-split`) reads no port and passes the plan through unchanged; otherwise the previous head is the previous completed run's bundle's `github.head_sha`, through the ledger's evidence pointer. It creates `--out` and writes the admitted `run.json` and, for a spend, `context-pack.json`, then appends, in this order: `admission` (`no-spend`, `reused`, `deferred` or `spend`), `deferral` (deferred only: §5's code), `slot` and `lease_commit` (a held slot only, above), `reserved_aeu` (the reservation for a spend, else `0`), `tier` (the tier the LLM stage runs at for a spend, else the plan's), `degrade` (`full` after a full-to-lite degrade, else `none`), `run_digest` (`sha256:<hex>` of the admitted `run.json`), `pack_digest` (a spend only) and `review` (`true` for a spend only). When admit fails once it took a slot (the admission after the slot, or the documents), `slot` and `lease_commit` alone are appended and the job exits 2, so release settles the reservation and releases the slot, or finds it already released. The carry is decided on the evidence pointer admit reads first; admit refuses a ledger state whose pointer is another by the time it builds the pack (a run completed in between), before any slot is taken. Exit 0 once written, 2 otherwise.

- **`decide`'s outputs and `publish`'s inputs** (#60 ST-14, 04 §5, D5 A): `assay decide --config <plugins-toml> --artifacts <dir> --out <dir>` reads `ASSAY_NEEDS` holding exactly the nine jobs before it (`guard`, `open`, `plan`, the three gates jobs, `admit`, `review`, `release`) and refuses any attempt but `1` before it reads a token. plan's, the gates jobs' and admit's outputs are read only from a job whose result is `success` (any other is passed to `authenticate` as that result, which refuses it); admit's are checked against plan's `review` and `tier` as admit writes them. Then it reads `[assay].ledger_repo`, `ASSAY_LEDGER_TOKEN` (the ledger's files: state, push and command records), `ASSAY_GITHUB_TOKEN` (the App's: reviews, the range's commit identities, labels, reactions, timeline, command comments), `ASSAY_RUN_TOKEN` (the live PR, its REST file list, the pinned commits, the previous run's bundle) and `ASSAY_VERDICT_APP_ID`/`ASSAY_VERDICT_BOT_ID`. The artifacts are read from `<artifacts>/<name>/<file>` for the names plan published only, each name one plain path component and each file a regular file reached without a symlink, under the size each document allows. It creates `--out` and writes `state.json` and, for an authenticated run only, the bundle `run-inputs.json` (§6a) before it, then appends `bundle` (`true` exactly when the bundle was written) and `bundle_digest` (`sha256:<hex>` of its exact bytes, written only with `bundle=true`). `state.json` is the channel from `decide` to `publish` in the same job (nothing PR-controlled writes there): one compact JSON object with sorted keys, at most 4 KiB, read strictly (no repeated or unknown key), exactly `{"verdict":"silent"}` (superseded, or yielding to a newer run: publish nothing), `{"verdict":"refused","reason":{"code","detail"}}` (a refusal: `gate-error` or `plan-mismatch`, a detail of at most 1 KiB without control characters, no `fp`) or `{"verdict":"decided","bundle_digest":"sha256:<hex>"}`. A refusal of the run is a state and exit 0, not an error. `assay publish --config <plugins-toml> --state <dir>` reads the same `ASSAY_NEEDS` (guard's identity and the review's `cost_aeu`), `ASSAY_PERSIST` (the upload step's outcome, exactly `success`, `failure`, `cancelled` or `skipped`), and the same tokens and ids; `state.json` and `run-inputs.json` are read from `--state` as the artifacts are (the bundle at most 96 MiB). It publishes nothing for `silent`; the `failure` check with the reason for `refused`, persisting nothing; and for `decided`, refuses a bundle that does not hash to the state's digest before any port, then publishes the decision re-read from the bundle, confirming the upload through the run's artifact store by sha256 only after `success` (anything else is `persist-error` on a trust-path or exec-surface PR and a warning on any other, with no evidence pointer written). `publish` writes no output. Each command exits 0 once done and 2 otherwise; the check `open` left `in_progress` is then closed by the reconcile (06 §4).

Later stories add each job's outputs here as they are written (`review`).

## 5. Decision (`assay.decision/1`)

`{decision_key, evidence_key, conclusion: success|failure|neutral|pending, reasons[{code, detail, fp?}], counts:{blocker,major,minor,nit}, advisory_blockers:[fp], dispositions:[{fp,code}], waived:[{fp,by}], degraded:[{role,reason}], rubric_version, inputs_digest}`.

`degraded` lists every degraded role of the LLM stage, sorted by role, once each: a specialist (`bugs`, `combined`, ...), `coordinator` or `verifier`, with the reason it reported (`cap`, `turns`, `timeout`, `malformed`, `unavailable`) or `missing` for a call that was due but never reported: a required role; on `full`, a coordinator over reviewer findings (wi-98c82b); on `full` or `lite`, a verifier when a blocker or major (a `04 §3` candidate) was raised. A role degraded for several reasons lists them all, distinct and sorted, joined with `, ` (`cap, timeout`). See `04 §5` rules 8b, 8c.

`pending` is expressed on GitHub as `in_progress` (never `neutral`, which counts as passing for required checks). It is used **only** for quota- or infra-deferred runs (`budget-deferred`, `slot-busy`, `infra-llm-unavailable`) on `trust-path`/`exec-surface` PRs, and for `slot-busy` on any agent-authored PR (`06 §1`), with at most 3 requeues after which the check becomes `failure`. The requeue counter and the deferral record `{repo, pr, head, count, resets_at}` live in the ledger (R3-11, R3-15); the `assay:llm-pending` label is a projection of that record, and such checks are excluded from `reconcile`'s staleness rule while a requeue is scheduled. A PR awaiting owner approval is **not** `pending`: it is `failure (trust-path-unapproved)` with label `assay:needs-owner`, and decide-only flips it when approval arrives. A required role that hit its own cap is `failure (required-role-degraded)`, which waiting cannot heal (`04 §5` rule 8).

Reason codes (closed enum, the cause of a check conclusion): `gate-failed`, `gate-error`, `gate-skipped`, `blocker-verified`, `majors-over-threshold`, `weigh-in-open-blocking`, `weigh-in-no-evidence`, `weigh-in-pending-triage`, `needs-split`, `infra-llm-unavailable`, `llm-degraded`, `required-role-degraded`, `trust-path-unapproved`, `plan-mismatch`, `publish-error`, `persist-error`, `bundle-expired`, `override`, `budget-deferred`, `slot-busy`, `base-not-protected`, `ambiguous-head`, `re-deciding`. (`base-not-protected` is a `failure` on a base where the check is not required, R3-03; `re-deciding` is the fail-safe completed state `open` publishes if a completed check cannot be reopened, `A-30`; `override` carries its scope `llm|all` in `detail`.)

Disposition codes (closed enum, what happened to an individual finding; not all are drops): `schema`, `evidence-missing`, `line-not-in-diff-moved`, `duplicate`, `duplicate-of-gate`, `suppressed-by-rule`, `dismissed-by-owner`, `waived-by-owner`, `verifier-rejected-downgraded`, `cap-exceeded`, `pre-existing`, `injection-suspect`, `no-trigger` (capped at `minor`, not dropped).

(`verifier-rejected-downgraded`: a refuted finding is downgraded to `minor` with the reason attached, not dropped, until the verifier's confusion matrix is measured on the corpus, `04 §4`.) `superseded` is an event (`RunSuperseded`), never a check conclusion or reason: a superseded run writes no check and no comment, but its ledger record and slot release still happen (R3-06).

## 6. Events (`assay.event/1`)

Envelope `{schema, job, idx, ts, run_key, run_uid, stage, kind, data}`. Each job appends to its own JSONL stream (`job`,`idx` order); there is no global `seq` and no inter-job in-memory state. Z4 merges the streams into the persisted bundle. Every state transition emits an event. Kinds:

`RunRequested`, `PlanComputed`, `Admitted{slot, reserved_aeu}`, `PreflightPassed|Failed{auth_method, cli_version, init_clean, builtins?}`, `GateStarted|Finished{plugin, exit, conclusion, duration_ms}`, `SpecialistStarted|Finished|Failed|BudgetExhausted{role, model, input_tokens, output_tokens, cache_read_tokens, cost_aeu, duration_ms, turns, stop_reason}`, `CoordinatorFinished`, `StageDegraded{stage, reason}`, `RateLimitObserved{status: allowed_warning|rejected, resets_at?}`, `FindingRaised`, `FindingVerified{verdict: confirmed|refuted|unclear}`, `FindingDisposed{code, fp?, from?, to?}`, `FindingPublished{url}`, `DecisionMade`, `CheckPublished`, `BundlePersisted{sha256}`, `WaiverApplied{who, fp}`, `OverrideApplied{who, reason}`, `FeedbackReceived{signal: reaction|dismiss|self-dismiss|resolved|anchor-changed}`, `RunSuperseded`, `BudgetDeferred`, `SlotBusy`, `LedgerWritten`, `SlotReleased`, `SlotReaped{run_uid}`, `PushRecorded{before, after, sender_id, forced}`, `CommandRecorded{command, actor_id, comment_id}`, `CommandRejected{command, actor_id, reason}`, `CommandVoided{comment_id, reason: edited|deleted|hash}`, `RetryGranted{role}`, `EvidenceReused{evidence_key}`.

In `FindingDisposed`, `fp` is the finding's fingerprint (§3) from the moment validation has computed it, which is when step 2 has located its evidence (#170): every transition recorded from then on names it (`line-not-in-diff-moved`, `pre-existing`, `cap-exceeded` for the role ceiling (with `from`), `no-trigger`, an `injection-suspect` of step 5, `suppressed-by-rule`, `dismissed-by-owner`, `duplicate-of-gate`, and the coordinator's `duplicate` and the verifier's `verifier-rejected-downgraded`, which name the merged or downgraded finding's own fingerprint, #263), and the schema requires it for those codes but `injection-suspect`. A transition before that has no fingerprint and carries none, rather than one made up: a document refused whole (`schema`, or `injection-suspect` when it holds the token), and a finding dropped by step 1 (`schema`), the egress scan (`injection-suspect`), the per-document cap (`cap-exceeded` without `from`) or step 2 (`evidence-missing`). `assay.event/1` is unreleased, so `fp` was added in place rather than as a new version.

In `PreflightPassed|Failed`, `auth_method` and `cli_version` are what `claude auth status` and `claude --version` (or, once read, the first call's `system/init`) reported, and `unknown` when the preflight failed before observing them (#83); `init_clean` is `false` on every `PreflightFailed`.

Local mode (#130, 02 §6) writes one stream for its whole run with `--events`, in emission order, which is `(job, idx)` order within each job. Its `run_key` is the recomputed plan's run key and its `run_uid` the local run's, and its jobs and stages are: `plan` (S1) `PlanComputed`; `gates-static` (S2s), `gates-lint` and `gates-test` (S2b) `GateStarted` and `GateFinished{plugin, exit, conclusion, duration_ms}` per gate, a gate the local runner does not run (temper, Weigh-In) included, with no exit or conclusion; `review` (S4) `SpecialistStarted`, then `SpecialistFinished`, `SpecialistFailed` or `SpecialistBudgetExhausted` (followed by `StageDegraded{stage: review, reason}` when the review did not complete), one `FindingDisposed` per validation transition and one `FindingRaised` per kept finding; `decide` (S7) `DecisionMade`. Events carry only assay's own words (roles, codes, plugin names, numbers), never model or gate text. A recorded stream is `crates/assay-app/tests/fixtures/events/check-local.jsonl`, the mod's test fixture.

These streams support audit, metrics and the cost ledger (`06 §1`). They are an audit record, not an event-sourced aggregate (the domain `Decider` pattern applies inside `decide`, not across jobs). The verifier's live reject rate (QA-12) is computed from `FindingVerified`.

## 6a. Persisted run inputs (`assay.run-inputs/1`)

`{schema, run_uid, evidence_key, documents[{job: plan|gates-static|gates-lint|gates-test|review, file, sha256, text}], inputs, rubric_version, decision, events[], carry, github}`, written by `decide` as `run-inputs.json` in its own artifact (`02 §5`). `documents` holds every input document Z4 authenticated, as UTF-8 text exactly as its job published it and with the digest that job published: the plan's `run.json`, then each gate document in job and plugin order, then the review documents in the order reported (a document that is not UTF-8 is a persist failure, not an escape). `inputs` is the domain's `DecisionInputs` exactly as decided, `decision` an `assay.decision/1` document, `events` the run's events ordered by `(job, idx)`. `carry` is the re-review carry set (`04 §7`, #224): `{findings[{fp, file, line, end_line?, class, severity, verdict?, title, trigger?, evidence}], omitted[{fp, reason: cap|refused|deleted-side}]}`. `findings` are the run's carried findings still open after it and its own findings that stand (not refuted), at most 256, one per fingerprint, most severe first (then carried before new, then in order): each where its evidence is at head (or was last published, if not found there), its severity and `verdict` as last verified (`verdict` absent if never re-verified; a finding not re-verified this run keeps both), its title and trigger (model text, the verifier's claim), and `evidence`, the tree's lines it matched, searched for again at head. A refuted finding is not carried. Where one fingerprint is carried and raised again, the fresh text is kept at the higher of the two severities, so a re-raise never lowers a carried finding without the verifier. `omitted` lists open findings left out: `cap` past the 256, `refused` for one the carried intake would refuse, `deleted-side` for one on deleted code (the base side), which has no location at head. A carried finding whose evidence is found at a head path the intake would refuse (a rename) stays where it was last published. The next run seeds its carry set from the previous completed run's bundle, only after the bundle hashes to its evidence pointer, names the pointer's run (attempt 1) and parses strictly, and only when the carry-over is kept (a rebase or force-push resets it; dismissals are command records, not part of it); every field is then checked as carried model text (`read_carried`), and one refused record refuses the set. A bundle over 96 MiB is not written (persist failure). `github` is the GitHub state snapshot `inputs` were built from (`04 §5`, #58), added in place while `assay.run-inputs/1` is unreleased (as `carry` was): `{lists{owners, approvers, maintainers, agents: [{id, login}]}, author, head_sha, range, pushers[], push_clock, approvals[{review, reviewer, submitted_at, status, reason?}], commands[{comment_id, actor_id, created_at, head_sha, body_sha256, command, args[], status, reason?}]}`. `lists` are the lists judged by (for decide-only, already narrowed by the base tip). `range` is `{status: within, users[], unattributed}` (the GitHub users who authored, by git author, or committed a counted commit, and whether a counted commit has no GitHub user) or `{status: needs-split}`. `pushers` are the senders of push records that are not clean merges from base. `push_clock` is null when no push record names the head. An approval's `status` is `ineligible`, with `reason` one of `not-privileged|maintainer|agent|author|in-range|pusher|unattributed-range|range-too-large` (eligibility is judged first), or else `counted`, `before-push`, `no-push-clock` or `unsubmitted`, with no `reason`. A command's `status` is `void` (with `reason` `deleted|edited|hash|author|app`), `ineligible` (with its reason), or `valid`, `other-head` or `before-push-clock` (with no `reason`). Review and comment ids are positive integers. Times are UTC RFC 3339 with `Z`.

## 6b. Status (`assay.status/1`)

`assay status [--json] [--pr <n>] [--full]` (#126) renders one PR's assay state as this document (or, without `--json`, the same facts as text, with each `--full` body indented under its finding and its control characters shown as U+FFFD), so the mod and scripts never parse check markdown, comments or `gh` output. `{schema, source: ci|local, repo, pr, branch, head_sha, local_head_sha, stale, check, decision, refused?, tier, gates[], findings[], weigh_in?, viewer, fetched_at}`:

- `check` is the `assay-verdict` check on the PR head (`{conclusion, status, url}`), or null when there is none. Only checks whose app id is the configured App count: a same-named check of another app is ignored, and two App checks with the verdict name are refused (A-27). `gates` are the App's `assay / gate: <plugin>` checks.
- `decision` (`{conclusion, reasons, reasons_digest, counts, degraded, advisory_blockers}`), `tier` and `weigh_in` are read only from the `assay.run-inputs/1` bundle (§6a) the check's `output.text` evidence pointer names, after its sha256 matches, its run is the pointer's and its decision key is the check's. `decision` and `tier` are null (and `weigh_in` absent) only when there is nothing to read: no App verdict check, a check carrying `open`'s `pending:<run>:<seq>` stamp (a run in progress), or a decided check whose run persisted no bundle. A decided `pending` verdict (its check stays `in_progress`), such as a budget deferral, carries its decision.
- `refused` (#218) is `{reason}`, present only for a run refused before the rubric, so a refusal reads differently from a run that never decided: the App's verdict check is completed `failure` and its `output.text` names neither an `inputs_digest` nor an evidence pointer, exactly as `publish` writes a refusal (a decided run always writes its inputs digest, so one that only failed to persist is not refused). `reason` is the one reason code (§5's closed list) the check's `output.title` carries, `assay: failure (<code>)`, the one part of the check that holds the code as closed vocabulary alone; it is never read from the summary's prose or from any other app's check. A refusal check that is not completed `failure`, a title of any other shape or code, or a text with a pointer but no inputs digest is refused (wi-b5affa). Absent for every other check, and never on a `local` document; the schema enforces both, and requires `decision` and `tier` null and no `weigh_in` beside it.
- `weigh_in` is `{state}`, the domain's Weigh-In code (§2.2): `clear`, `open-blocking`, `pending-triage` or `no-evidence` (on which the decision fails, so it is never reported as clear); absent when the gate is not required.
- `findings` are the decision's gate and reviewer findings, one per fingerprint (`fp`, which is also the `finding_id` `/assay waive` takes) at the highest severity carrying it. `title`, `class`, `file`, `line`, `url` and, with `--full`, `body` come only from the App's own inline comment for that fingerprint (already sanitised, 05 T8); a gate finding without one is titled `<plugin>: <rule>`, cleaned as the check summary cleans it. `disposition` is the decision's last for the fingerprint. `waivable` is exactly the domain waive rule (R-08(a), #59): true when every gate finding carrying the fingerprint has a rubric-waivable (gate, rule); a reviewer finding is never waivable.
- `viewer` is the caller's login and whether the base P10 lists name them owner or agent.

Anything read that does not parse exactly is refused (wi-b5affa), except a finding comment's title, class or body, which is left out rather than guessed. Inputs are capped and refused past the cap: 1,000 check runs on the head, 1,024 App review comments, 4,096 findings, 1,024 reasons and 1,024 degraded roles; each list is read from the port under one more than its cap, so a list cut there is refused rather than read as complete. `fetched_at` is the caller's clock reading, parsed as an RFC 3339 UTC date-time before anything is read. `source` is `ci` for this form.

`assay status [--json] --local` (#130, 02 §6) writes the same document with `source: "local"` from local mode's report, never from GitHub: `{schema, source, local_head_sha, tree, local_tree, stale, check, decision, tier, gates[], findings[], fetched_at}`. `tree` is the tree fingerprint the shown result was checked at (null when there is none), `local_tree` the working tree's now, and `stale` is true when both are present and differ (with a null `tree` the schema requires `stale: false`). `check` is `{conclusion, status}` with no `url` (`completed`, or `in_progress` with a null conclusion for a `pending` decision), or null with no local result. `gates` are `{plugin, conclusion}`, one per plugin at its worst conclusion. `findings` carry `fp`, `severity`, `class`, `title`, `file`, `line` and `waivable: false` (no waiver applies locally) and no `url`, `body` or `disposition`. A local document has no `repo`, `pr`, `branch`, `head_sha`, `viewer`, `weigh_in` or `refused`; a `ci` one has no `tree` or `local_tree`; the schema enforces both. The same caps apply, and a report that does not read exactly (`assay.local-check/2`, `advisory: true`, no unknown field, at most 8 MiB) is refused; one of the older `assay.local-check/1` format is refused as such, asking for a rerun. Its goldens are `local-fresh.json`, `local-stale.json` and `local-missing.json`. The schema is `schemas/status-1.schema.json`; its golden documents (`schemas/fixtures/status/valid/`) are the mod's test fixtures.

## 6c. Ledger records (`assay.ledger-cost/1`, `assay.ledger-push/1`, `assay.ledger-command/1`, `assay.ledger-state/1`, `assay.ledger-lease/1`, `assay.ledger-lock/1`, `assay.ledger-grant/1`)

The files of the ledger repository (06 §1, ADR-19, ADR-23), written only by `assay-ledger-writer` (ADR-26) and read back as untrusted input (T23): a file over 4 MiB (so that its base64 form fits in one 8 MiB API response), a record line over 4 KiB, a line that is not exactly one JSON object, a record that is not byte for byte what assay writes for it (fields in the writer's order, no spaces, serde_json's escapes, the state document with its final newline: assay's writer is the only writer, so any other form was written by someone else), an object that repeats a key, an unknown field or a value in another form than the one below refuses the whole file (wi-b5affa), and the job then treats the ledger as unreadable (06 §1). Every write is compare-and-set on the file's version, re-read by the same reader before it is sent, and retried on a conflict at most 5 times; a write that cannot be confirmed (an attempt went unanswered and the file then moved) is an error, never a conflict, so no change is applied twice. Times are UTC to the millisecond, `YYYY-MM-DDTHH:MM:SS.mmmZ`; AEU amounts are exact decimal strings in dollars as `Aeu` displays them (`"0.74"`, `"2"`), never JSON numbers. Every record carries its contract id in `schema`.

- **Cost records**, `ledger/YYYY-MM.jsonl`, one JSON object per line: `{schema, run_uid, run_key, repo, pr, head_sha, tier: full|lite|micro, roles[{role, aeu}], aeu, kind: reserved|final, cancelled, at}`. `role` is a reviewer role, `coordinator` or `verifier`, each at most once; `cancelled` is never true on a `reserved` record; `at` lies in the file's month. At most one record per (`run_uid`, `kind`): an append that finds one writes nothing, also in the month before when the 24 hours before its `at` reach into it, so back-fill is idempotent across a month boundary (R3-16).
- **Push records**, `pushes/<repo_id>/<pr>.jsonl`: `{schema, run_uid, pr, seq, kind: opener|push, before?, after, sender_id, forced, at}`, written by `open` (#54): `kind: opener` for `opened` (the head the PR arrived with; its sender is the opener, not a pusher; no `before`, `forced` false) and `kind: push` for each `synchronize` (`before` required). `at` is the triggering workflow run's `created_at`. `seq` is 1 on the first line and one more on each next one; one record per `run_uid`. The push clock of a head is the `at` of the latest record whose `after` is that head, the opener's included (04 §5).
- **Command records**, `commands/<repo_id>/<pr>.jsonl`: `{schema, run_uid, pr, comment_id, actor_id, command, body_sha256, created_at, at}`. `command` is 1 to 256 characters without a control character; one record per `comment_id`.
- **Per-PR state**, `state/<repo_id>/<pr>.json`, one document: `{schema, repo_id, pr, evidence?: {run_id, run_attempt, sha256}, decision?: {run_id, sha256}, evidence_records[{evidence_key, bundle_sha256, llm, tier}], deferral?: {repo, pr, head, count, resets_at?, flag}, actor_counters[{actor_id, count}]}`. At most 256 evidence records (keys distinct) and 256 counters (actors distinct); absent parts are omitted.
- **Lease refs (#71)**, the commit message of a parentless empty-tree commit a ref of the ledger points at, one canonical line (at most 1 KiB; one trailing newline a host adds is accepted): a slot lease `refs/heads/slot-N` carries `assay.ledger-lease/1` `{schema, run_uid, repo, pr, reserved_aeu, expires_at}`; the per-head publish lock `refs/heads/lock-<repo_id>-<head_sha>` carries `assay.ledger-lock/1` `{schema, run_uid, repo, head_sha, expires_at}`; a retry grant `refs/heads/retry/<repo_id>/<pr>/<head_sha>/<role>` carries `assay.ledger-grant/1` `{schema, run_uid, repo, pr, head_sha, role, at}`. A ref is taken only by creating it, and deleted only by `git push --force-with-lease` against the commit read (06 §1). A lease is live up to and including its `expires_at`. A lock or grant whose document names another repository id, head, PR or role than its ref is refused, as is any lease the reader cannot read exactly; an unreadable slot lease is never reaped, and makes the whole acquisition or read fail as an unreadable ledger (06 §1) until the owner removes it. A grant is consumed by deleting its ref, after which the ref can be created again: the once-per-head-and-role retry limit (06 §1) is enforced by decide-only from its command records, not by ref creation, and that enforcement is #287. Schemas: `schemas/ledger-lease-1.schema.json`, `ledger-lock-1`, `ledger-grant-1`.

Stream records and the state document name the repository id and PR of their path, and a record of another one is refused. The budget read (06 §1) takes each run's `final` record, else its `reserved` one, counted when written at or after 24 hours before the read, across the month boundary; a lease adds its `reserved_aeu` unless its run is already counted. Schemas: `schemas/ledger-cost-1.schema.json`, `ledger-push-1`, `ledger-command-1`, `ledger-state-1`, with goldens under `schemas/fixtures/ledger-*/`.

## 6d. Context pack (`assay.context-pack/1`)

The Z4 half of the context pack (02 §2, 04 §3), built by `admit` (#72) and carried in its outputs with its sha256: `{schema, run_uid, run_key, suppress, dismissals[{comment_id, actor_id, fp, reason}], prior[]}`, compact JSON. `suppress` is base `.assay/suppress.toml` as read at the pinned base, unparsed (§1 does not fix its format yet), or null without the file; over 64 KiB `admit` fails. `dismissals` are read only from the ledger's command records (§6c), never from comment text: a record counts when its command is exactly `/assay dismiss <fp> <reason>` (single spaces, 16 lowercase hex digits), its actor is eligible by 04 §5's rule: a privileged identity of base P10 that is no agent and not (a) the PR's author, (b) a GitHub-attributed author (co-authors included) or committer of any commit in the range, or (c) the sender of one of its `push` records (an opener is not a pusher); a clean merge from the base (04 §5) counts toward neither (b) nor (c), and a range commit with an author or committer that is no GitHub user counts as authored by every owner, which, as base P10's lists hold owners and approvers together, leaves no identity eligible (fail closed); and its comment still stands as recorded: present, `created_at` as recorded, never edited (`updated_at` equal to it) and its body hashing to `body_sha256` (05 T21). They are in record order, at most 256; later ones are left out, which suppresses less. `prior` is the previous completed run's `carry.findings` (§6a), read through the ledger's evidence pointer by the same checks as the re-review's carry seed, only when the carry-over is kept, and empty otherwise; a kept carry with no evidence pointer, or a bundle that cannot be read or checked, fails `admit`. The schema is `schemas/context-pack-1.schema.json`, with goldens under `schemas/fixtures/context-pack/`.

## 7. Model runner port

```rust
pub trait ModelRunner {
    fn preflight(&self) -> Result<AuthProof, PreflightError>;       // auth method, cli version, init cleanliness
    fn run(&self, call: ModelCall) -> Result<ModelResult, RunnerError>;
}
pub struct ModelCall {
    role: Role,                        // specialist | coordinator | verifier
    system_prompt_file: BundleRef,     // fixed per run, identical across roles
    user_prompt: Prompt,               // context pack first, then role instruction
    schema: &'static JsonSchema,       // one findings schema for all specialists (prompt-cache sharing)
    tools: &'static [Tool],            // Read, Grep, Glob only
    max_turns: u8, budget_aeu: Decimal, timeout: Duration,
    add_dir: PathBuf,                  // read-only PR tree
}
pub enum ModelOutcome { Ok(Structured), BudgetExhausted, TurnsExhausted, Timeout, QuotaExhausted, Malformed }
```

**Preflight as built (#83).** The sketch's `preflight` is two steps in `assay-app`, not a method of `ModelRunner`. `preflight(variables, &impl CliProbe, pinned)` runs before any call: it fails on any job variable named `ANTHROPIC_*`, `CLAUDE_CODE_USE_*`, `AWS_*`, `GOOGLE_*`, `CLOUD_ML_*` or `VERTEX_*` (set, even empty), then asks the CLI (`CliProbe`, implemented by `ClaudeHeadless` under the calls' own environment and empty working directory, 30 s and 64 KiB per command) for `claude --version` (one line `<version> (Claude Code)`, which must equal `claude_cli`) and `claude auth status` (one JSON object, no repeated key, requiring `loggedIn: true`, `authMethod: "oauth_token"` and `apiProvider: "firstParty"`), giving an `AuthProof`. Every `ModelResult` carries its call's `system/init` as read; `AuthProof::check_first_call` judges the first call's with the clean-init rule (§8), and that call's output is not used unless it passes. Every failure is the LLM-unavailable policy (`infra-llm-unavailable`) with a `PreflightFailed` event; a pass gives `PreflightPassed`. A failure the token causes (`NotLoggedIn`, `AuthMethod`) carries the link to `docs/operations/token-rotation.md` in its message (`PreflightFailure::runbook`, 06 F4, #93).

`BudgetExhausted`/`TurnsExhausted` are distinct, non-retried outcomes: the CLI returns no structured output on them, but the `error_max_budget_usd` / `error_max_turns` `result` messages **do** carry `total_cost_usd` and `modelUsage`, so the real cost is ledgered (F2). The role is marked degraded and visible in the check summary. Adapters: `ClaudeHeadless` (OAuth), `ClaudeApi` (API key, same CLI), `Replay` (recorded outputs).

## 8. Headless invocation profile (the Z3 contract)

```
cwd = an empty directory (the same absolute path for every call)
env: CLAUDE_CODE_OAUTH_TOKEN; ANTHROPIC_API_KEY / AUTH_TOKEN / cloud vars UNSET and asserted;
     CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1 (moot with no process-spawning tool; kept as belt and braces)
claude -p < <prompt file: context pack, then role instruction> \   # prompt on stdin, never argv (wi-9fe37e)
  --output-format stream-json --verbose \        # --verbose is required with stream-json under -p; result carries structured_output + total_cost_usd
  --json-schema <schema> \
  --append-system-prompt-file <base-sourced bundle> \
  --exclude-dynamic-system-prompt-sections \     # move per-user/cwd context out of the system prompt (cache reuse)
  --restricted \                                 # >= 2.1.248: no command-running tools, no WebFetch, file tools confined to working dirs, only managed settings + --settings loaded
  --safe-mode \                                  # no CLAUDE.md, plugins, hooks, MCP or skills from anywhere; auth still works
  --settings '{"disableAllHooks":true,"permissions":{"deny":["Read(//proc/**)","Read(//sys/**)","Read(~/**)","Read(//etc/**)"],"blockReadsOutsideWorkingDirectories":true}}' \
  --tools "Read,Grep,Glob" \                     # no Bash at all
  --add-dir <PR tree, read-only>  --permission-mode dontAsk \
  --max-turns <n> --max-budget-usd <aeu_cap>     # = cap exactly (not x1.2); client-side estimate that can overshoot by one response
```

`permissions.blockReadsOutsideWorkingDirectories` is **nested under `permissions`** and requires CLI ≥ 2.1.257 (v1 wrongly put it at the top level, where it is ignored). Under `dontAsk`, reads outside the working directories need no allow rule and are denied by default, so the deny rules and this key are defence in depth; Read-deny coverage of Grep/Glob is best-effort.

Rules:
- **The prompt travels on stdin**, not as an argument (wi-9fe37e): Linux caps one argument at 128 KiB (`MAX_ARG_STRLEN`), which a context pack can exceed, and stdin cannot be mistaken for an option. The runner writes the prompt to an anonymous temporary file before the CLI starts and opens it as the child's stdin (no pipe, so no writer can block). `assay doctor` (#84) verifies that the pinned CLI reads its `-p` prompt from stdin with this flag set.
- **No `Bash`** in Z3. The built-in read-only Bash set (`cat`, `ls`, `grep` …) bypasses `--allowedTools`; `Bash(rg:*)` allows `rg --pre <cmd>` (arbitrary execution) and `git show --output=<path>` writes files (both reproduced by reviewers). `--tools` removes the tool; allowlists do not. `--restricted` removes command-running tools independently. Diff and base-file contents the reviewers need are put in the context pack; Grep/Glob replace `rg`.
- `--bare` is never used (it ignores the OAuth token). `--safe-mode` also disables `--plugin-dir`, so prompts travel as files. `assay doctor` checks that `--restricted` and `--safe-mode` can be combined on the pinned CLI; if not, `--restricted` with `--settings` is used alone.
- The `stream-json` `system/init` message is inspected (#121). It must be the first message, appear once and repeat no key in any object, and it is **clean** only when `claude_code_version` equals `claude_cli`, `mcp_servers` is empty, `tools` is exactly `Glob`, `Grep`, `Read` (in any order, each once), every `plugins` entry is a built-in (`path` `builtin`, `source` `<name>@builtin`) and every plugin, skill and agent is on `claude_cli_builtins`, with no name listed twice; anything else (or an unreadable init: a missing or mistyped field, a plugin entry with other keys than `name`, `path` and `source`, a list over 256 entries, a name over 128 bytes or with a control character) ⇒ preflight failure `init-unclean`. **Built-ins are allowlisted, not absent**: Claude Code 2.1.296 ships built-in mods (`cc-plugin-agents-md`, `cc-plugin-telemetry`, `cc-plugin-plugin-authoring`), skills and agents that `--safe-mode`, `--bare` and `disableAllHooks` do not stop and no documented headless switch disables; their set varies by environment, so the allowlist is taken from `assay doctor`'s observed diff where the review job runs. `assay doctor` fails when the observed built-ins differ from the allowlist in either direction, so a CLI pin bump without a matching allowlist update is a reviewed trust-path change. `PreflightPassed|Failed` carry the observed set (§6).
- **Mod canary** and **AGENTS.md canary** (`assay doctor` and the monthly canary workflow, #121): one call with this profile's exact argv in a throwaway checkout whose `HOME` holds `.claude/settings.json` naming a user-scope mod in `env.CLAUDE_CODE_PLUGIN_DIRS`, and whose working directory and `--add-dir` tree each hold a skills-folder mod (`.claude/skills/<name>`) and an `AGENTS.md` and `CLAUDE.md` telling the model to end every reply with a canary word, written in two parts so only a model that followed it writes it whole. Each mod's `session.start` hook writes a marker. The canaries fail if a marker appears, a planted mod is named in `init.plugins`, the word (any ASCII case) appears anywhere in the transcript, its nonce appears in a message the model wrote (anything but the tool results, which quote the planted files), or the call did not answer. That AGENTS.md is not loaded under `--safe-mode` is one build's behaviour, not a documented contract, so it is observed like the other flags. `CLAUDE_CODE_PLUGIN_DIRS` cannot be passed to a headless call.
- Hooks: **`init` carries no hooks field**, so hooks are excluded structurally (`--restricted` loads only managed settings and `--settings`; `disableAllHooks`) and proven absent by the **hook canary**: a base-sourced canary hook is planted at user, project and in-tree scope in a throwaway checkout, `--include-hook-events` is passed, and the canary fails the doctor if any hook event appears or the marker file is written. A flag that is accepted but ineffective is therefore caught by observation, not by trusting the flag.
- **Fence canary** (monthly and in `assay doctor`): a prompt that asks the model to `Read //proc/self/environ`; the run must show the call in `permission_denials` and the token must not appear in the output.
- `--add-dir` directories count as working directories for `blockReadsOutsideWorkingDirectories` (documented; `assay doctor` still verifies behaviourally; if not, the PR tree is mounted at a path allowed by an explicit `Read(...)` rule instead).
- `assay doctor` verifies each flag against the pinned CLI (`A-10`) and fails on mismatch. The CLI version is pinned in base config and is part of the evidence key.
- **Flag verification, hook and fence canaries as built (#84).** `assay doctor --profile <plugins-toml> <claude-program>` (a form beside the session checks of #121) fails when the pin is below 2.1.257, then runs the preflight (§7) and one canary call with this profile's exact argv followed only by `--include-hook-events`, in a throwaway checkout whose `HOME`, working directory and `--add-dir` tree each hold a `.claude/settings.json` with a base-sourced command hook on every session, prompt, tool and stop event that writes a marker. The stdin prompt carries a fresh word and asks for `Read //proc/self/environ`, a read of a file in the `--add-dir` tree and a read of a file outside both working directories; the appended system prompt file carries another word. It reports `cli-minimum`, `preflight` (completed by the call's init), `profile-accepted` (the argv, `--restricted` with `--safe-mode` included, answered; a refusal is reported; the fallback above then applies, and switching the pinned argv to `--restricted` with `--settings` alone is the follow-up), `permission-mode` (`dontAsk` in the init), `stdin-prompt` and `system-prompt-file` (the reply repeats both words), `hook-canary` (no marker, no hook message in the stream), `fence-canary` (`/proc/self/environ` in `permission_denials`, the token in no encoding the egress scan reads), `add-dir` (the tree file was read) and `outside-read` (the outside file was denied and its word never seen), then each flag with the checks that show it; `--exclude-dynamic-system-prompt-sections`, `--max-turns`, `--max-budget-usd` and `--include-hook-events` are reported as accepted only. A-10 stays unmeasured until the canary runs against the pinned CLI.
- `autoContinueAtUsageLimit` (wait-and-resume; user/managed scope only) is off; a usage-limit error is classified `QuotaExhausted`.
- **Rate-limit events.** The stream's `rate_limit_event` carries `rate_limit_info{status: allowed|allowed_warning|rejected, resetsAt?, utilization?}` and fires with `status: allowed` routinely, so assay keys only on `rejected` and `allowed_warning`. A `setup-token` OAuth token carries only the `user:inference` scope and does not expose plan utilisation, so there is no utilisation-based pause (`A-13`).
- **Cost accounting.** `total_cost_usd` exists only in the final `result` message; SIGTERM yields exit 143 with no result record, losing both output and cost. assay therefore does not kill on its own mid-run accounting: the hard stops are `--max-budget-usd = cap`, `--max-turns` and a wall-clock timeout (on timeout the cap is charged as the cost). A `review` job killed from outside (cancelled by a newer push, job `timeout-minutes` ≤ 40) is charged at the run cap by the `release` job, and the per-PR cooldown and 24-hour sum count `admit`'s `reserved` record anyway (`06 §1`, R3-06).
- **Prompt-cache sharing** applies only between calls with the same model, the same system prompt and the same schema/tool block; the specialists share one findings schema, the coordinator and verifier (different schemas, possibly different model tier) do not. `06 §3` models only the shared part.
- The model secret is still present in the claude process's initial environment. `Read(//proc/**)` is denied, no tool can spawn a process, egress is restricted (`05` T2), and the output channel is scanned (§3). This is defence in depth, not a proof (`05` residual).

## 9. Git hygiene for Z1, Z2s and Z4 (fetching PR objects as data)

Every git invocation that touches PR-controlled objects runs with: `GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_ATTR_NOSYSTEM=1`; `-c core.hooksPath=/dev/null`; `-c protocol.allow=never -c protocol.https.allow=always`; `-c transfer.fsckObjects=true -c fetch.recurseSubmodules=false -c fetch.fsckObjects=true`; `-c attr.tree=4b825dc642cb6eb9a060e54bf8d69288fbee4904` (the empty tree: a bare repository otherwise reads HEAD's `.gitattributes`, and `--text` does not stop `-diff` from turning numstat counts into `-`; `check-attr --source` still reads the PR's attributes to police them); `--no-ext-diff --no-textconv` on every diff; every git process leads its own process group, its stdio are spooled to anonymous files rather than pipes (so no descendant can hold a reader past the deadline), a run is complete only when the leader has exited and no live process is left in the group, and on timeout or an over-cap output the whole group is killed with the system `kill` and verified gone through `/proc` (a host without a usable `kill` fails closed before any git runs, `06 §5` F22); `-c diff.renameLimit=1000` and a wall-clock cap on `git diff` (`-M` is O(n²); on timeout the PR is `needs-split`, not hung); an **object-only repository with no worktree** in Z4, created in an absent or empty directory (never over an existing repository whose config the flags above would not override). `git diff --numstat` reports `-` for binary files: line counts for tiering use `--text` and treat any remaining `-` as maximum size (forces `full`). The in-tree `.gitattributes` is policed by `git check-attr` (§2.1), not neutralised.
