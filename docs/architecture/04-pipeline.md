# 04 · Pipeline: stages, tiering, reviewers, decision

Status: **v1.2**.

## 1. Stages

Every job holding a secret or a write token runs only on `github.run_attempt == 1` (`02 §1`); recovery is a fresh run. S2s/S2b run in parallel with S1a–S6. **Reviewers are not given gate findings**; Z4 removes LLM findings that duplicate a gate finding (same file, line within ±3, same `class`) as `duplicate-of-gate`. This removes the latency dependency and keeps one source of truth. The price is accepted: a finding later removed as a duplicate may already have consumed verifier budget. Dismissals and `suppress` rules, by contrast, are known before the verifier because `admit` hands them to Z3 in the context pack (§4 step 6).

## 2. Plan and tiering (deterministic, S1; recomputed by Z4)

Inputs: the file list from `git diff --raw base_sha...head_sha` (the name-status with both sides' modes, for symlinks and gitlinks) and `--numstat --text` on fetched objects (asserted equal to the REST list when that list is not truncated; the REST list caps at 3,000 files), the parsed manifests at both SHAs, and base `.assay/`. No model. The lists are compared as the set of paths either names, both sides of every rename, so rename detection may differ between git and GitHub. A complete REST list (fewer than 3,000 files, as many as the PR's `changed_files`) must name exactly git's paths; a truncated one (3,000 listed, more changed) only paths git lists, and git must then list at least `changed_files` distinct paths. Any other REST list, a repeated path, a diff past its cap, or a base `.assay/` that lacks `plugins.toml`, holds a symlink or submodule, or does not parse fails `plan` (wi-b5affa: refused, not modelled). Until the Z2s include scan (#64) reports its targets, every changed path counts as one, so no change is `trivial`.

### 2.1 Filtering

Excluded from model context and line counts, **by base-defined globs only**: lockfiles' text, `*.min.*`, `*.snap`, binary files, and the globs in base `.assay/globs.toml` for generated output. In-file markers such as `@generated` headers are ignored. **`.rs`, `build.rs`, shell/CI/script files and manifests are never excluded**, wherever they live (`vendor/` included). Excluded files are still named to reviewers. Exclusion affects the model's workload only: it never suppresses a gate finding and never hides a trust-path match. Line counts come from `git diff --numstat --text`; a `-` (binary) result is treated as maximum size and forces `full`. A zero-line result that is not in the trivial allowlist (binary-only, snapshot-only, lockfile-text-only with no dependency change) is `micro`.

### 2.2 Trust paths and exec surface (R-07)

Any match forces tier `full`, adds `meta`, and requires the owner approval review (rubric rule 4). Detection runs on the parsed base/head, not just file names, and **matches both sides of a rename** (old path and new path), so moving code out of `**/auth/**` does not leave its risk class. Two reductions keep approval fatigue bounded: a change to `.claude/temper-baseline.json` in which every count only goes down (or is unchanged) is not a trust-path change; and exec surface is detected precisely (below), not by any new package.

**Trust paths:** `.github/**` (workflows, actions, dependabot), `.assay/**`, `.claude/**`, `REVIEW.md`, `AGENTS.md`, `CLAUDE.md` (any directory), `**/CODEOWNERS`, `.gitattributes`, `.githooks/**`, temper's `protected` globs, `clippy.toml`, `.clippy.toml`, `rustfmt.toml`, `.rustfmt.toml`, `rust-toolchain*`, `deny.toml`, `.cargo/**`, `scripts/**`, `xtask/**`, `Makefile`, `justfile`, `package.json`, `Dockerfile*`; and, from TOML-parsed manifests, any change to `[lints]`/`[workspace.lints]`, `[patch]`, `[replace]`, `[workspace] members|exclude`, `rust-version`, `edition`, or the test switches (`test`, `doctest`, `harness`, `autotests`, `autobenches`). If a manifest cannot be parsed, the conservative fallback treats it as changed. Repos add globs in `.assay/globs.toml`. For the assay repo itself: the extras in `02 §7`.

**Exec surface** (compile-time code execution and supply chain), computed by `cargo fetch --locked` followed by `cargo metadata --locked --offline` run by the pinned base cargo on a sanitised manifest-only copy (`03 §2.1`), then diffing the package set base vs head: any `build.rs` (including under `vendor/`); any crate with a `proc-macro` target; `[build-dependencies]`; a **new or bumped package that has a `custom-build` or `proc-macro` target**; any package whose `source` changed (registry/git/path); path-dependency additions. A new or major-bumped *registry* package with no such target is not exec surface: it tiers at least `lite`, adds the `cargo deny` gate, and is routed to the owner by temper H-16's hook as before. Other changes under `vendor/**` tier at least `lite` and are never excluded from review.

### 2.3 Tiers (first match wins, evaluated in this order)

| Tier | Condition | LLM | Expected AEU | Cap |
|---|---|---|---|---|
| 1 `needs-split` | filtered changed lines > 5,000 | none | $0 | $0 |
| 2 `trivial` | every changed file (both sides of a rename) is in the base **docs allowlist** and no trust path or `include_*!` target (below) | none | $0 | $0 |
| 3 `full` | trust path or exec surface changed; or filtered lines > 150; or a base risk glob (`**/auth/**`, `**/crypto/**`, `**/migrations/**`, `**/unsafe*`, `**/*.sql`) | `bugs`, `security`, `design` (+`meta`), coordinator, blind verifier | $1.50 (`meta`: $1.70) | $2.30 ($2.60) |
| 4 `lite` | filtered lines 21–150, or a lockfile dependency change, or a new/bumped registry package, or other `vendor/**` changes | `combined`, blind verifier (≤ 3 candidates) | $0.50 | $0.74 |
| 5 `micro` | everything else: 0–20 filtered lines in any file outside the docs allowlist | `combined-micro` (≤ 8 turns), no verifier; findings capped at `major`, advisory, and never counted by rubric rule 7 | $0.15 | $0.25 |

**Docs allowlist (explicit; replaces v1's `*.md` anywhere and `docs/**` of any type):** root `README.md`, `CHANGELOG.md`, `LICENSE*`, and `docs/**/*.md`, `docs/**/*.txt`, `docs/**/*.{png,jpg,svg}`. **Never trivial**, even inside those globs: `**/SKILL.md`, `**/agents/*.md`, `**/commands/*.md`, `**/hooks/**`, `.kb/**`, `REVIEW.md`, `AGENTS.md`, `CLAUDE.md`, anything under `plugin/**` or `skills/**` (these are executable agent instructions), and any file referenced by `include_str!`, `include_bytes!` or `#[doc = include_str!(..)]` from a `.rs` file at base or head (found by the Z2s scan; such a README becomes a doctest; a reference the scan cannot place, such as a computed path, keeps every file out of `trivial`). Repos extend the allowlist only through `.assay/globs.toml`.

Thresholds are `A-05`, tuned by replay. A repo may add risk globs; it may not lower a tier for trust paths/exec surface. Size is a poor proxy for risk, so code never lands in `trivial`: even a one-character `<`→`<=` change gets the `micro` reviewer.

**Matching (fail closed both ways).** Every glob matches the whole repository path. Lists that raise a tier or protect a file (trust paths, risk globs, code that is never excluded, the never-trivial list, `vendor/**`, `build.rs`) match ignoring ASCII case and also when any ancestor directory matches; file names that tools discover in any directory (`AGENTS.md`, `CLAUDE.md`, `REVIEW.md`, `CODEOWNERS`, `.gitattributes`, `.claude/`, `.cargo/`, `.githooks/`, `clippy.toml`, `rustfmt.toml`, `rust-toolchain*`, `deny.toml`, `Makefile`, `justfile`, `package.json`, `Dockerfile*`) match in any directory. Lists that lower one (the docs allowlist, exclusions) match exactly and case-sensitively. A risk glob, a package change or a trust path also refuses `trivial`, and an empty file list is `micro`. A path that is not canonical (empty, an empty, `.` or `..` segment, a leading `/` or `"`, a `\` or a control character) is a trust path. A symlink or gitlink is never docs and never excluded. A changed file at or under the source root of a workspace `custom-build` target (the directory of a `[package] build` script) or `proc-macro` crate (its directory and its `[lib] path`), at base or head, is exec surface; a root outside the repository makes every file exec surface. Every package whose `build` is not `false` also has its build sources as a root: the `.rs` files of the crate outside `src/`, `tests/`, `benches/` and `examples/` (for the root package, top-level `.rs` files and `<dir>/mod.rs`). A manifest whose exec roots differ between base and head is itself exec surface. Path crates reachable as build-dependencies or from a proc-macro are added from the package-set diff. Every top-level key of the temper baseline other than `totals` and `updated` must be unchanged for the lowered-counts reduction to apply. A binary numstat forces `full` but adds no lines, so it never makes a PR `needs-split` on its own. The `classes` order is `trust-path`, `exec-surface`; `tier_reasons` are the conditions of the chosen row that hold, with the codes `split-size`, `docs-only`, `trust-path`, `exec-surface`, `full-size`, `binary-file`, `risk-glob`, `lite-size`, `lockfile-dependency`, `registry-package`, `vendor` and `micro-size`.

### 2.4 Budget gate and drafts

`admit` decides (`06 §1`). If projected spend breaches the cap, a **non-trust-path** `full` degrades to `lite` (event `BudgetDeferred`, stated in the summary); the degrade travels in `admit`'s outputs (`budget.tier_degraded_from`) and Z4 accepts it when recomputing required roles (R3-27). A busy semaphore is its own reason, `slot-busy`, distinct from quota deferral: for agent-authored PRs it never yields an `llm-degraded` success; the check stays `in_progress` and requeues like a deferral (R3-06). A trust-path/exec-surface PR is **never** degraded: its LLM stage is deferred (`budget-deferred`) and the check stays `in_progress` (`pending`) until capacity returns, requeued at most 3 times, after which it fails with `infra-llm-unavailable` so a stuck PR is visible rather than silent. Deferral is distinct from a role that exhausted its own cap (rule 8b). Draft PRs run gates only; the LLM stage runs on `ready_for_review`.

### 2.5 Provenance

Commit trailers (`Claude-Session`, `Co-Authored-By`) and signatures are recorded for telemetry and for the Weigh-In evidence rule's convenience messages. **No rule is looser because provenance claims "human"**: agent sessions can omit trailers and sign with the owner's key. What is strict is identity: agents commit under identities listed in base `.assay/agents` (numeric ids), and rules keyed to "agent-authored" use those ids (`H-08`). Authorship is computed from GitHub-attributed users (per commit over the Z4 git range, and the `sender_id` of the ledger push records, §5), never from `Co-authored-by:` trailers, which anyone can add.

## 3. Reviewer roster (S4–S6)

All specialists share a fixed system-prompt bundle (identical across roles for cache reuse), read-only `Read/Grep/Glob`, the same cwd, and the same context pack placed **before** the role instruction. Bundles live in `plugin/prompts/<version>/` (v1: `combined`, `combined-micro`, `verifier`); the bundle hash, SHA-256 over each file's versioned path and bytes, is the evidence key's `prompt_bundle_hash` (02 §3).

**Blindness.** `bugs`, `security` and the `combined` roles receive the diff and tree but **no PR title, body or commit messages** (an agent's own "this is intentional because…" anchors the reviewer). `design` and `meta` receive intent text inside the untrusted envelope. The verifier receives only `{file, line, class, one-sentence claim, trigger}`, never the specialist's rationale, and is a different model tier from the specialists (the split is chosen by ablation, `A-14`).

**Severity, operationally** (in every prompt): `blocker` = causes data loss, security compromise, crash, or an incorrect result in normal production use, with a concrete triggering input or execution path; `major` = incorrect behaviour on a reachable path, or violation of a stated project rule, with a concrete trigger; `minor` = real but low-impact; `nit` = style the formatter does not catch. From `major` up a `trigger` is mandatory; without one the finding is capped at `minor` (`no-trigger`).

| Role | Focus | Tier | Max turns | Cap (AEU) |
|---|---|---|---|---|
| `bugs` | Logic, edge cases, error handling, concurrency, resource bounds; **greps callers of every changed symbol** and traces data flow | full | 25 | $0.60 |
| `security` | Injection, authz, secrets, unsafe deserialisation, new dependencies and `build.rs`; treats PR text as hostile | full | 20 | $0.50 |
| `design` | API shape, layering vs AGENTS.md crate map, test adequacy, docs freshness; cites rust-craft rule IDs from the base cheat-sheet (no shell, no temper agent) | full | 20 | $0.50 |
| `meta` | Only for trust-path/exec-surface changes: what authority the change grants, what check it weakens; primary object is the base→head diff of the trust files | full + trust | 15 | $0.30 |
| `combined` | bugs + security + design in one pass | lite | 20 | $0.50 |
| `combined-micro` | Short, focused pass on a tiny diff | micro | 8 | $0.25 |
| `coordinator` | Group findings by root cause (`group_id`), merge duplicates, apply "what not to flag", rank | full | 10 | $0.30 |
| `verifier` | Blind, one call per candidate blocker/major **or carried-over finding** (together ≤ 5 full, ≤ 3 lite; none in micro); try to refute; `confirmed`, `refuted` or `unclear` plus one line | full, lite | 8 each | $0.08 each (≤ $0.40 / ≤ $0.24) |

Sums: full = 0.60+0.50+0.50+0.30+0.40 = **$2.30**; with `meta` **$2.60**; lite = 0.50+3×0.08 = **$0.74**; micro **$0.25**. Caps are provisional: M2 sets the specialist and lite caps at the measured p90 spend and M3 the full-tier caps (`A-21`). A PR whose pack exceeds 120 KB is sharded by **dependency cluster** (changed files plus their direct importers) into ≤ 3 shards; shards run **sequentially** (so a run never exceeds 4 concurrent model processes), each shard runs the full specialist set, and the run cap scales by the shard count: **$6.90**, or **$7.80** with `meta`.

**Required roles** per tier: full = {`bugs`, `security`, `design`} (+`meta` on trust paths); lite = {`combined`}; micro = {`combined-micro`}. A missing required role, a failed coordinator or an unavailable verifier makes the LLM stage `degraded`/`unavailable` (rubric rule 8). Nothing downgrades silently.

**"What not to flag"** (anti-noise block in every prompt, from Cloudflare/Anthropic practice plus Rust-specific additions): style a formatter handles; anything a linter or gate already reports; pre-existing issues (mark `pre_existing`); speculative performance; naming bikesheds; `unwrap`/`expect` in tests; generated/vendored code; concerns the compiler or type system already guarantees (data races in safe code, use-after-free, exhaustiveness, `Send`/`Sync`); integer-overflow worries with no reachable input; hedged speculation ("could", "might") without a concrete trigger; "add tests/docs" without naming a behaviour. Dismissed-finding classes are reviewed monthly and promoted to `suppress` rules.

**Context pack:** changed-file list with status; filtered unified diff (hunks ±30 lines, ≤ 120 KB); the base REVIEW.md and AGENTS.md; base-side contents of deleted files/hunks (so `side: LEFT` evidence is locatable); prior open findings on re-review (as claims to re-verify). The pack is assembled in two parts: PR-derived material by `review`, and the suppress list, valid dismissals and prior findings by `admit` from App-authored records (never from PR comment text). Specialists may Read/Grep the full head tree.

## 4. Validation and verification (order matters)

Mechanical validation runs as one library function twice: non-authoritatively in Z3 before the verifier (so a model is never asked to confirm an unsupported claim) and authoritatively in Z4.

1. *Schema*; over-length/unknown fields rejected (`schema`).
2. *Evidence location.* The normalised `evidence` span (shared normaliser, `03 §3`) is searched in the **whole** head file, or the base file for `side: LEFT`/deleted code. Zero matches ⇒ drop (`evidence-missing`). One or more ⇒ `line` is **relocated** to the unique nearest match (not dropped for drift). `kind: omission` anchors on the enclosing function's signature, which must exist, and requires `expected_behavior`. Renames are resolved through `git diff -M`.
3. *Placement.* Inline comments require the line to be in a diff hunk. Otherwise the finding moves to the summary (`line-not-in-diff-moved`; it still counts for the rubric). `introduced_by: interaction` findings must cite the changed hunk and a real `caller` span; they anchor on the changed hunk and mention the caller. `pre_existing: true` is honoured only if the cited line is outside the diff **and** `introduced_by != interaction`; otherwise the flag is reset.
4. *Trigger* required from `major` up, else capped at `minor` (`no-trigger`).
5. *Injection screen* (heuristic, last line of defence, not the primary control): URLs outside the allowlist (repo URLs, `rust-lang.org`, `docs.rs`, `owasp.org`), images, HTML, `@mentions`, `suggestion` fences, token-shaped strings, imperative text addressed to the reader/agent ⇒ `injection-suspect`. Two or more in a run raise a visible warning.
6. *Suppression* applies only to LLM findings: base `suppress` rules and owner-valid dismissals (§6) are applied **before** the verifier using the lists in the context pack (Z3 runs the shared fingerprint function non-authoritatively for this; Z4 recomputes), and duplicates of gate findings are removed by Z4 afterwards (§1).
7. *Coordinator* groups by root cause, merges duplicates, applies the cap (≤ 8 inline: blockers first, then majors by confidence).
8. *Blind verifier* per candidate. `refuted` ⇒ **downgraded to `minor` with the reason attached** (not dropped) until the verifier's confusion matrix is measured on the corpus (what share of seeded true positives it kills, what share of known false positives it passes); `unclear` ⇒ one level down; `confirmed` ⇒ unchanged. Every transition emits an event (`FindingVerified`, `FindingDisposed`); QA-12 alerts on a live reject rate outside 10–60% over ≥ 20 runs. Carried-over findings share the verifier cap (§7). Candidates (blockers and majors after step 4) are judged blockers first, then by `confidence`, then in order, up to the tier's cap; a candidate past the cap keeps its severity, unverified. The verifier's answer is read strictly (wi-b5affa): exactly `{verdict, reason}`, the reason one line of printable ASCII of at most 200 characters that passes the step-5 screen; anything else is malformed, retried once, then the verifier is degraded (`malformed`), never read as `unclear`. The first call that ends without a verdict stops the stage: verdicts already given stand, every other candidate is shown as an unverified major at most (`06 §6`), and a `StageDegraded` event names the reason. `unclear` has no disposition code, so its `FindingVerified` is its record. The live reject rate is `refuted` over all `FindingVerified` verdicts, over the distinct runs that emitted one (#91).

## 5. Decision rubric v1 (S7, pure function)

Inputs: validated gate documents; validated verified findings; the Z4-recomputed plan; the GitHub state snapshot (approvals, command records for waivers, override, dismissals, retry and Weigh-In ack, owners, approvers, maintainers, agent identities, pusher set, push clock, open PRs on the head); policy from base config.

```
1  required gate failed | gate-error | gate-skipped (minus findings waived, see below)  → failure
2  base ref not in protected_bases                                    → failure (base-not-protected; the check is not required there)
2a more than one open PR on head_sha into this protected base          → failure (ambiguous-head)
3  tier == needs-split                                                → failure
4  (trust path | exec surface changed) and not owner_approved(head)   → failure (trust-path-unapproved, label assay:needs-owner)
5  weigh-in gate required and reports open-blocking | pending-triage | no-evidence → failure
6  llm_blockers == block and a verified blocker (not pre_existing)    → failure (blocker-verified)
7  llm_majors == block and count(distinct group_id; major; confirmed by the verifier;
      not pre_existing; from a non-micro role) >= 3                   → failure (majors-over-threshold)
8a LLM stage deferred (budget-deferred | infra-llm-unavailable) and (class in block_on_infra_for or on_infra_failure == block),
   or slot-busy and (the above or the PR is agent-authored)
                                                                      → pending (in_progress, label assay:llm-pending, requeued ≤ 3 times, then failure infra-llm-unavailable)
8b a required role degraded (own cap/turns/timeout/malformed after retry) and (class in block_on_infra_for or on_infra_failure == block)
                                                                      → failure (required-role-degraded); waiting cannot heal a role cap. Remedy: `/assay retry <role>` by an eligible owner
                                                                        (a one-shot ledger grant; the next run re-runs all required roles with that role's cap ×1.5) or `/assay override llm`
8c LLM unavailable or a required role degraded, otherwise            → success + visible llm-degraded warning
9  else                                                               → success
waive    /assay waive <finding-id>: removes ONE human-decision gate finding (raised baseline, ask exception, gate-config drift,
         test-inventory decrease, manifest switch) from rule 1. Never clippy, build, test or deny failures. Recorded in the decision.
override /assay override llm|all <reasons_digest> <reason> → neutral, original reasons retained. reasons_digest = sha256 of the sorted current reason
         codes, printed in the summary; void if any reason is ADDED. `llm` neutralises only rule 8; `all` is the break-glass. Weekly report lists both separately.
         Neither ever neutralises rule 2: on an unprotected base `neutral` would only let a stale check pass after a retarget (R3-03).
```

- `owner_approved(head)` (and the eligibility of **every** privileged action: waive, override, dismiss, retry, Weigh-In ack): a numeric GitHub user id in `.assay/owners` ∪ `approvers`, lists that hold **privileged identities only** (accounts never authenticated in any agent-reachable context: no Claude GitHub App authorisation, no `gh` token on a machine where agents run, no PAT given to a session; the owner's daily account is a `maintainer` and is never eligible; R3-01, `H-06`, `H-13`), that is **not** (a) the PR author, (b) a GitHub-attributed author or committer of any commit in the PR range, nor (c) the `sender_id` of any push record for this PR in the ledger. One rule, used verbatim by R-07, R-08, P10, T9, ADR-16 and §6.
  - **Range and attribution (b).** The range is computed from git objects in Z4 (`git rev-list base_sha..head_sha`) and resolved per commit, never from `GET /pulls/{n}/commits`, which returns at most 250 commits; a range of more than 250 commits is `needs-split` (R3-22). A commit whose author or committer is not a GitHub user (apart from `web-flow` as committer) counts as authored by every owner, so the approver is required.
  - **Push records (c).** `open` appends `{before, after, sender_id, forced, at}` to `pushes/<repo_id>/<pr>.jsonl` in the ledger for `synchronize` events only, with `at` = the triggering workflow run's `created_at`; the `opened` sender is recorded as `opener`, not as a pusher. Non-push events (`reopened`, `ready_for_review`, `edited`, dispatch, re-runs) never change the pusher set (R3-07).
  - **Clean merge-from-base.** A commit, and a push record whose `after` is such a commit, is excluded from **both** (b) and (c) when Z4 finds two parents, `parent1 == before`, `parent2` an ancestor of the base, and a tree equal to a conflict-free `git merge-tree --write-tree`. So the owner pressing "Update branch" (merge) does not disqualify their own approval; "Update with rebase" rewrites committers and does.
  - **Push clock** = the `at` of the latest push record whose `after == head_sha` (for a head that arrived with `opened`, the `at` of the `opener` record). `open` never writes `started_at` on an existing run, so a re-run or requeue never moves the clock.
  - **Approvals.** For each reviewer id, the latest review on `head_sha` whose state is not `COMMENTED` counts; it must be `APPROVED`, not dismissed, with `submitted_at` later than the push clock (R3-23). An approval ignored for timing is shown in the summary ("approval at T ignored: before push at T′").
  - **Commands are events, not state (R3-02).** Any writer can edit or delete another user's comment, keeping its `user` and `created_at`. decide-only therefore parses a command only from the payload of the `issue_comment.created` event that triggered it, checks eligibility and the push clock there, and appends an App-authored command record `{comment_id, actor_id, created_at, head_sha, body_sha256, command, args}` to `commands/<repo_id>/<pr>.jsonl` in the ledger. Every later `decide` (pipeline and decide-only) reads command records, never comment bodies. At read time it re-fetches the comment; the record is void if the comment was deleted, if `updated_at != created_at`, or if the body hash differs, so an edit can only revoke a command, never grant one. Dismissal and override reasons are taken from the record. A command comment with a non-null `performed_via_github_app` is rejected (reviews carry no such field, so this filter cannot cover approvals).
  - **Eligibility lists** are read from `base_sha`; decide-only intersects them with the lists at the current tip of the protected base, so revoking an approver takes effect at once while adding one waits for a new run (R3-26, narrowed).
  - Co-author trailers are ignored. Because an owner-authored PR has no eligible owner approver, the **approver account** (`H-13`, a second account that never pushes and is never agent-reachable) is the expected approver for those PRs; the alternative is the break-glass account's ruleset bypass outside assay (`06 §4.5`).
- **Lifetime and binding of privileged actions** (R3-13). Lifetime is per head except for dismissals; eligibility is judged when the command record is written.

  | Action | Lifetime | Bound to |
  |---|---|---|
  | approve | head | `commit_id == head_sha`, after the push clock |
  | waive | head | finding fingerprint and gate-document digest; carried to a new head only if both are unchanged |
  | override | head | reasons digest (an added reason voids it) and scope `llm`/`all` (R3-12) |
  | dismiss | PR | fingerprint, `class` and severity ceiling (`03 §3`, R3-25); eligibility judged at record time, so a later push by the dismisser does not revive the finding |
  | retry | head | one-shot ledger grant per (head, role) (`06 §1`, R3-14) |
  | weigh-in-ack | head | set digest (§9 rule 2) |
- While `llm_blockers == advisory` (default), rule 6 does not fire: verified blockers are published prominently with the 🔴 marker and counted in `assay report` for the promotion decision (`QA-05`). While `llm_majors == advisory` (default), rule 7 does not fire. Both promotions are per-repo base-config changes (a trust-path change, so an H-decision) and each needs its own measured precision.
- A gate finding is never lowered by LLM output or by dismissal; only a scoped waiver removes a human-decision gate finding. Majors are counted by distinct `group_id` (three call sites of one root cause are one). `majors_block_threshold = 3` is `A-07`; a density-aware rule is evaluated on M5 data.
- Override and waiver by whole-verdict break-glass should be rare because waivers cover the legitimate same-PR cases (a human-approved baseline raise, an `#[expect]` exception, a test removal) without waiving unrelated failures such as Weigh-In. The weekly report counts both.
- **Degraded roles (rules 8b, 8c).** `decide` derives the required roles from the recomputed tier and classes (§3; after `admit`'s full→lite degrade, R3-27) and reads which specialist roles completed, which reported a degraded outcome, and how the coordinator and verifier ran. When the stage completed, a required role that neither completed nor reported is degraded with reason `missing`; a role degraded on any shard is degraded; a failed coordinator or verifier is always degraded (as `coordinator`, `verifier`), and on a blocking class or policy that is `failure required-role-degraded`, never a deferral (Weigh-In default wi-9fd143). On `full`, a coordinator that did not run is accepted only when there are no reviewer findings, else `coordinator: missing` (wi-98c82b); on `full` or `lite`, a verifier that did not run although a blocker or major (a §3 candidate) was raised is `verifier: missing` (`micro` has no verifier). Each degraded role fires 8b or 8c once and is listed, sorted by role, in the decision's `degraded`, which the check summary renders; a role degraded for several reasons keeps them all, joined (`cap, timeout`). A deferred or not-run stage is rule 8a's; it reports no missing role.
- The rubric is data (`rubric/v1.toml`) plus one pure function; `rubric_version` is recorded.

## 6. Publish, dismissal and feedback (S8)

- **Check run** `assay / verdict` (or `assay / verdict @<base>` for a non-default protected base), App-authored (`assay-verdict`), the only check in branch protection, exactly one per (head SHA, name), with `output.summary` (counts, reasons, tier, degraded roles, AEU, the Weigh-In blocking-set digest, the reasons digest for `override`, ignored approvals, how to dismiss/waive/override), **no `output.annotations`** (they accumulate across updates, R3-11; location data is in inline comments and the `assay / gate: <name>` checks), `output.text` rendering the ledger state (`decision_key`, evidence and decision pointers, `inputs_digest`), and `external_id = decision_key` (two-phase, `02 §5`). Per-plugin checks `assay / gate: <name>` are additional, non-required.
- **Summary comment** upserted by marker (write-if-changed). **Inline comments** one per published finding with a hidden Z4 fingerprint marker and a footer inviting 👍/👎; a fingerprint is posted at most once per PR; when a carried finding's re-verification says the defect is gone, the thread is resolved with a note.
- **Sanitisation** (Z4, last step): HTML, images, `@mentions` stripped; fenced blocks allowed only with info strings from a small allowlist (never `suggestion`); links only to files/lines of the repo; token-shaped strings and the free-text egress scan (`03 §3`) applied; lengths capped. The publisher does not parse model Markdown to decide what is safe (wi-b5affa, #175): every ASCII punctuation character of model prose is backslash-escaped, so no link, image, autolink, HTML, code span, fence, emphasis, table, heading, quote or list can start; `@` and `#` become their fullwidth forms (no mention, email autolink or cross-repository reference), `://` and `www.` are written `[:]//` and `www[.]` (no extended autolink), `gh-` before a digit, in any case, is written `gh[-]` (no `GH-<n>` reference), leading whitespace is dropped (no indented code) and control and format characters become U+FFFD. Model prose therefore renders as plain text. The only live links are the permalinks the publisher builds (`https://github.com/<repo>/blob/<head>/<path>#L<n>`, path percent-encoded, none for a path with an empty, `.` or `..` segment or a control or format character), and the only fences its own, around the repository's evidence and caller lines, tagged from a closed list (`text`, `rust`, `toml`, `json`, `yaml`, `sh`) and longer than any backtick run inside. Accepted residual links: GitHub still links a bare commit SHA to that commit in this repository, and the repository's own custom autolink references (set by its admins) still match; both stay within the repository or its admins' configuration. Title, body, trigger, expected behaviour, fix and rule are capped at the findings schema's lengths before escaping (rule 100), code at 20 lines and 1,000 characters.
- **Inline comments** are written after the verdict, under the per-head lock and only while the verdict check carries this run's decision key; otherwise the run yields. At most 8 per run (most severe first, so blockers then majors, then by confidence high, medium, low, unstated, then input order; one per fingerprint). The fingerprint marker is the comment's first line, `<!-- assay-finding <fp> -->`; the fingerprints already posted are read from the App's own review comments on the PR (at most 1,024, else nothing is posted), so a re-run posts no duplicate. The footer gives the fingerprint and the `/assay dismiss` command. Each gate gets its `assay / gate: <name>` check (`success`, `failure` or `neutral` as the gate concluded; `failure` for an errored or skipped gate), keyed by the decision key and left alone once completed under it.
- **Dismissal.** `/assay dismiss <fp> <reason>` is honoured only from an eligible owner (§5, P10) and only through its command record (§5). It may suppress LLM findings of any severity, **never** gate or Weigh-In findings. A dismissal or thread-resolve by the author/pusher/agent identity is recorded as `FeedbackReceived{self-dismiss|resolved}` and **does not suppress**. Dismissal suppresses by fuzzy fingerprint match, same `class` and severity ≤ the dismissed severity, for the life of the PR (§5 lifetime table); a higher-severity match is published with "previously dismissed similar" (`03 §3`).
- **Approval, waiver, override and dismissal** are re-evaluated by the decide-only workflow. Its triggers are only those that run the default-branch workflow file (`02 §1`): `issue_comment[created]` commands, `pull_request_target` `labeled`/`unlabeled` on `assay:*` labels, and an hourly `schedule` poll at an off-peak minute for PRs in `pending-approval` (its Actions minutes are costed in `06 §3`; GitHub may delay or drop scheduled runs, so the bound is best effort). The expected sequence is: owner approves by review, then posts `/assay recheck`; if they forget, the poll picks the approval up within about an hour. A `pull_request_review` → `workflow_run` nudge (a trigger-only workflow with no permissions or secrets as the target of a default-branch `workflow_run` workflow that re-decides from current API state; its payload is never trusted and a PR can delete it, so it never replaces the poll) is adopted only after its M1 canary (`A-32`, R3-18). No model runs; the bundle is the one the ledger's evidence pointer names, and decide-only persists its own decision bundle (`02 §5`).
- **Command grammar (closed, R3-24).** One command per comment, on the first line, not inside a blockquote or code fence (so a quote-reply of agent text is not a command), exact tokens: `/assay recheck`, `/assay waive <finding-id>`, `/assay override llm|all <reasons_digest> <reason>`, `/assay dismiss <fp> <reason>`, `/assay retry <role>`, `/assay weigh-in-ack <set_digest>|none`. Unknown commands are rejected with a reply. Per-actor command counters live in the ledger and are checked first (T12). A command or an `assay:*` label never dispatches a run; at most it sets a flag on the PR's ledger deferral record (`06 §1`).
- **Feedback labels** for eval: reactions (response rate is reported alongside precision, since silence is not agreement), owner dismissals-as-wrong, and "a later commit changed the anchor lines".

## 7. Re-review

- A new push is a new run. The **target** the specialists review is always the full cumulative diff; the increment since the last *completed* run (`git range-diff` against the merge-base; the cumulative diff when the previous head is unreachable, e.g. after a force-push, or there is no completed run) is marked "new since last review" to focus attention. This avoids the blind spot where a small push invalidates earlier-reviewed code. Because the specialists re-read the cumulative diff, **an incremental run costs the full tier cost** (`A-02`); only verification of carried findings is incremental.
- Tier is computed on the cumulative diff.
- **Carried-over findings are re-judged**, not string-matched: open findings go to the blind verifier with the question "is this defect still present at head?", sharing the verifier cap with new candidates (≤ 5 full, ≤ 3 lite; carried findings first, by severity). "Anchor line no longer present" means *needs re-verification*, not *resolved*. Carried findings that exceed the cap stay open as of their last verification, are listed in the summary as "not re-verified (cap)", and are excluded from rules 6–7 until re-verified. In `micro` (no verifier) carried findings are re-checked only deterministically (anchor evidence still present at head); if it is, they stay open and advisory; if it is not, they are marked "needs re-verification" and the thread is left open.
- A rebase/force-push resets the carry-over set but keeps dismissal records.
- A dismissed fingerprint (valid dismissal, recorded as a command record) stays suppressed for the life of the PR, within its class and severity ceiling (§5 lifetime table).

## 8. Replay and evaluation

- **Decision replay (R-09).** `assay replay --verify <run>` loads the persisted `RunInputs` bundle (including the GitHub state snapshot and full finding bodies) and recomputes `decide`, diffing against the recorded decision. Scope: the decision. Model re-execution is optional and uses a recorded or fresh run explicitly flagged as non-reproducible. Bundles expire after 90 days; replay of an expired bundle is an error, not a pass. `assay_app::replay_decision` (#74) implements it over the evidence pointer: the bundle is read under its 96 MiB cap and must hash to the pointer's sha256, record the pointer's run (attempt 1), keep documents that still hash to their recorded digests and an evidence key equal to its inputs', and recompute under the recorded rubric version to the recorded decision, compared byte for byte in canonical JSON (compact, keys sorted). Only a match passes. A missing, expired, over-cap or unparseable bundle, a re-run pointer and another rubric version are errors; a digest, run, document, evidence-key or decision disagreement is a mismatch, reported by the first differing byte offset and field (a JSON pointer naming only the recomputed decision's keys), never by quoting the bundle. The model stage is reported as recorded only and non-reproducible. The CLI subcommand waits for the artifact-store and ledger adapters.
- **Corpus** `corpus/`: ≥ 30 labelled cases at ship (20 dev / 10 test), grown from shadow-period real defects to ≥ 140 (≥ 40 dev, ≥ 100 test) before QA-07 is claimed as a non-inferiority result; until then QA-07 is a descriptive report. Sources: (a) real Wet Ink PRs whose merged code later needed a fix (label = the fixing commit's hunks), (b) mutation-seeded defects (smoke only), (c) true-negative PRs for noise, (d) `corpus/inject/` hostile-text fixtures, (e) rebase/force-push and cross-file "consumer not updated" fixtures. Each case is labelled with the authoring model so same-family (self-review) recall is reported separately from human-authored recall.
- **Dev/test split.** Prompt work uses only `dev`; `test` is not read during prompt iteration and is refreshed from new real defects each quarter.
- **Scorer.** Deterministic: a reviewer finding matches a label if it is in the same file, within ±10 lines of the fixing hunk, and the `class` maps to the label's class. No LLM judge.
- **Method.** k = 3 runs per case. A prompt/rubric change is accepted when no case flips from ≥ 2/3 detected to ≤ 1/3 and the true-negative noise rate does not rise by more than the Wilson-aware margin (reported with n). A mean-difference threshold of "5 points" is not used: one case is 3.3 points at n = 30.
- **Cost.** A pass over 30 defect-skewed cases averages ≈ $1.00 AEU ⇒ **≈ $30**; k = 3 ⇒ **≈ $90 per evaluation**, drawn from a **separate eval ledger** (cap $150 AEU/month), run off-peak, with a cheaper-tier screening pass before the final run. Replay runs never draw on the production daily cap.
- **Shadow mode (M5).** ≥ 4 weeks and ≥ 40 PRs beside the current SaaS. assay posts as its own bot with a separate non-required check (visible, so agents' fixes are not contaminated by only one tool; both tools are visible, accepted). Labelling samples **randomly from all findings of both tools, stratified by tool and agreement, blind to source**, by a fixed protocol; shared false positives therefore get labelled. Report n, intervals and reaction response rate.
- **Promotion** of `llm_blockers` and `llm_majors` follows `QA-05`; there is no rolling-30 test.

## 9. Weigh-In checkpoints (R-11, G2)

**What exists (verified in the weigh-in repo, v0.6.0, 2026-10-10).** The ledger is local (git common dir) and never pushed. Journals under `.kb/_ledger/journal/<session>.jsonl` are written by a repo-local hook (`.claude/hooks/weigh-in-journal.sh`) that only runs in cloud sessions (`CLAUDE_CODE_REMOTE=true`) and is **not part of the plugin** (`plugin/hooks/hooks.json` has no journal hook); local desktop sessions write none. Decisions are atoms in `.kb/_intake/decisions/` and commit trailers `Weigh-In: <id> decided <X>`. Item ids are `sha256(session ‖ normalised question)`, so a marker alone cannot be matched to an item. `blocks:` is free text set by the raising agent; `open --json` is an unversioned dump of the internal `Item`. An omitted or unrecognised `door` parses to `unsure` and `authority` to `authority` (marker parsing), while the *triaged* `door`/`authority` fields are `None` until `/weigh-in` triage; `Status::is_open` covers Raised, Triaged, Grounded, Presented and Deferred, and `Route::Default` items become `Defaulted` after triage and are not open. Nothing is signed.

**Consequence.** CP2 as first drafted (fold journals, match markers in the diff, accept `Weigh-In: none`, trust atoms/trailers) was an honour system and partly unimplementable; and a blocking set built on agent hints would block nearly every PR before triage. G2 is therefore **staged**, and triage state is part of the contract.

**CP1 – local pre-push (ledger present, advisory).** `assay check --local` runs `weighin open --json` filtered to the current branch (`item.branch`) and reports (a) *blocking* items: open and triaged with `door != two-way`, `authority == authority` or a non-null `blocks`, and (b) *pending-triage* items: open with triaged `door`/`authority` still `None`. It blocks the push on (a) and warns on (b). A convenience (P9); `--no-verify` bypasses it.

**CP2 – CI evidence gate (`assay / gate: weigh-in`).** Prerequisite, requested from Weigh-In (`D-WI`, owner H-02): (1) ship the journal hook in the plugin so every session surface commits a journal; (2) `weighin ci-check --json --base <ref>` with a **versioned** output that joins journal `item_id` ∪ atom front-matter ∪ trailer id and reports open items with `status`, **triaged** `door`/`authority` (null when untriaged), `kind` and `blocks` (as an enum `merge|release|none|unknown`; missing = `unknown`, never `none`); (3) append-only verification of journals (below). The adapter rejects any output whose version it does not know (today's `open --json` is unversioned and is therefore used only in `experimental` mode).

assay's rules over that output:
1. **Blocking set** = open, triaged items where `blocks != none` **or** `door != two-way` **or** `authority == authority`, for every `kind` (a one-way authority *question* blocks just as an *assumption* does). **Pending-triage set** = open items whose triaged `door`/`authority` is null: reason `weigh-in-pending-triage`, a warning while the gate is `experimental`, a failure once it is required. The raising agent cannot opt out by labelling, and an untriaged item is never silently treated as non-blocking.
2. **Decisions need corroboration, once per PR rather than once per item.** A decision counts only if the commit adding it is GitHub-verified-signed by a key of an owner, **or** an eligible owner (§5, P10) posts `/assay weigh-in-ack <set_digest>` after the push clock (honoured only as a command record, §5), where `set_digest` is the sha256 of the sorted blocking item ids and their recorded decisions, printed in the check summary. The ack is void when the digest changes. A decision atom, journal event or trailer written by the agent proves nothing by itself.
3. **Evidence rule** (identity-based, per `§2.5`): if the PR author or any pusher/committer is an agent identity (`.assay/agents`) and the PR touches any non-docs file, the PR must contain **at least one** journal, or carry an eligible owner `/assay weigh-in-ack none`. (v1's "a journal for each cited `Claude-Session`" was vacuous for an agent that cites none.) A bare `Weigh-In: none` in the PR body is not evidence.
4. **Deferral** without trigger and resolve-by is open.
5. **Append-only check at event level.** The journal hook's `keep()` deletes a cut-short last line (`sed -i '$d'`) and re-merges after a container resume, and one session id can produce the same journal path in two PRs, so a byte-prefix test is wrong. The check is: every base journal line (by parsed event) is still present at head; a trimmed final partial line and additional lines are allowed; a missing or altered complete line fails.

**Until `D-WI` is delivered** the adapter runs `experimental`: non-required, using documented journal and atom formats (verified in M4 step 0, `A-11`), reporting only. G2 is then enforced by CP1 and by convention (`AGENTS.md`: settle Weigh-In before the session ends), and the summary says so. The marker-in-diff rule is dropped: markers are captured from chat into the ledger, rarely appear in diffs, and cannot be joined to items without the session.
